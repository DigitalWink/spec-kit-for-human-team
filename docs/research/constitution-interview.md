Findings behind the wayfinder map for adding a bounded, inference-first constitution interview to this fork.

## Proposal

### Content model

A strong Spec Kit constitution is a short, standing POLICY document — 5 to 7 numbered principles, under ~6,000 characters — whose only job is to make three downstream commands behave differently: /plan (fills `## Constitution Check` and ERRORs on unjustified violations), /analyze (extracts principle names + MUST statements, hard-codes "Violates constitution MUST" as CRITICAL), and /converge (cites principles as `Constitution II` in remediation tasks). Nothing else reads its content. Nothing validates it. A vague principle fails silently, so the authoring step is the only quality gate that will ever exist.

STRUCTURE (load-bearing, not cosmetic): H1 title; `## Core Principles`; one `### <Numeral>. <Short Name>` per principle — the `###` level under that exact H2 is what "principle name" means to an extracting LLM, and the numeral is what makes a violation citable; optional free-form `##` sections as an overflow valve for material that is real policy but not a principle; `## Governance`; the `**Version** | **Ratified** | **Last Amended**` footer. ZERO `[ALL_CAPS]` bracket tokens must survive — they are /converge's runtime signal for "unratified template, skip constitution checks", while /plan and /analyze have no such carve-out and will gate on placeholder text.

EACH PRINCIPLE carries four parts: (1) a short citable name; (2) one or more rules stated with a literal ALL-CAPS MUST / MUST NOT — MUST is the only enforcement trigger in the whole pipeline, and SHOULD is extracted but has no severity rule attached anywhere, so SHOULD buys nothing mechanical; (3) at least one measurable object — a number, a named file, a named tool, a named command, or a named forbidden construct; (4) a `**Rationale:**` line naming the failure the rule prevents.

THE TWO TESTS THAT DECIDE ADMISSION. Gate-restatement: the rule must be restatable, with no added information, as a yes/no question about a specific implementation plan ("Does this plan create more than 3 deployable units?"). If it cannot become a checkbox, /plan has nothing to fill and the principle is decoration. Forbidden-alternative: the rule must name the cheaper thing a competent engineer would otherwise do ("MUST NOT wrap a framework API in a repository layer", "mocked persistence MUST NOT substitute for the real database"). This is what lets the plan's Complexity Tracking columns — Violation / Why Needed / Simpler Alternative Rejected Because — actually be filled, and it is the single sharpest anti-platitude filter: a rule compatible with every possible implementation is not a rule.

WHAT IS EXCLUDED, and where it goes instead. Values and aspirations ("we value quality") — nowhere; cut. Descriptive overview prose ("this project is a React SPA with a Postgres backend") — cut; the empirical evidence is that instructions in context files are followed while repository overviews are not helpful and cost >20% inference overhead. Standard, widely-known defaults the agent already applies — cut; the constitution records what is NON-STANDARD about this project. One-time decisions ("we chose Postgres over Mongo") — an ADR; the constitution amends in place with a semver bump and has no supersede mechanism, so decision history silently eats the principle budget. Build/test/run commands and repo layout — AGENTS.md. Version- or file-path-specific detail that will be wrong in six months — the plan or config. Feature requirements — the spec; route them to the existing Scope Guard's `Next Actions` section.

GOVERNANCE must state three things the enforcing consumers do not read but humans need: the amendment route and who approves, the compliance-review expectation wired explicitly to the plan's `## Constitution Check` and /analyze's CRITICAL rule, and the consequence of a violation (blocked merge vs. documented exception). A principle with no stated consequence is decoration; a document with no amendment route gets ignored rather than revised.

DURABILITY AND HONESTY. Every principle must still be true after a framework upgrade, and must describe what the project already does or has committed to migrate toward on a dated plan. An aspirational MUST that most of the existing codebase violates produces a wave of CRITICAL findings on the first /analyze run and trains the team to ignore the whole document — the same false-positive collapse that kills static-analysis rollouts.

### Taxonomy (10 areas)

#### Negative scope and forbidden alternatives (the "never do" list)

*Scope: always ask*

**Why it matters.** This is the highest-signal, least-inferable content in any real constitution, and it is the only category that reliably produces principles that survive the inversion test. A rule stating what the project will NOT do discriminates between real design options; a rule stating what it values does not. It also maps perfectly onto the plan's Complexity Tracking table, which literally has a column named "Simpler Alternative Rejected Because". Every published constitution that reads as useful rather than generic has this content; every generated one that reads as filler lacks it.

**Inferable from repo.** Almost nothing, and that is exactly why it earns a question slot. Weak hints only: absent dependency categories (no auth library, no message queue, no multi-tenant schema), a self-hosted-only deploy config, an explicit non-goals section in README, closed issues labelled wontfix, and ADRs recording rejected options. Present these as candidate guesses to reject, never as inferred fact.

**Example question.**

> Name up to three things this project must never do, even when a change request seems to justify them. My guess from the repo: (A) stay single-tenant and self-hosted — no hosted or per-customer deployment; (B) no background job scheduler — everything runs in the request path or a manual CLI command; (C) no telemetry sent off-box. Recommended: A and C. Accept, edit, or replace.

**Example principle.**

```markdown
### VII. Single-Tenant, Self-Hosted Only

- The system MUST remain single-tenant. Plans MUST NOT introduce tenant-scoped identifiers on entities, tenant-aware query filters, or a shared control plane.
- The project MUST NOT ship a hosted or SaaS deployment path. Any request implying multiple customer organizations MUST be rejected at spec time, not designed around.

**Rationale:** Retrofitting multi-tenancy is cheap; carrying speculative tenancy plumbing on every query for a product that will never have it is not.
```

#### Testing and verification policy

*Scope: always ask*

**Why it matters.** It is the densest source of plan-time gates in the entire pipeline, it is the one area where the shipped template carries an opinionated default (Test-First NON-NEGOTIABLE) that users are documented as silently inheriting and then resenting, and its rules are the easiest to state with a measurable object. It is also the area where an aspirational MUST does the most damage: if the repo has no tests and the constitution says every change MUST be test-first, the first /analyze run produces CRITICAL findings on everything.

**Inferable from repo.** Very high. Detect test directories and naming conventions, the test runner and its config (pytest.ini/pyproject, jest.config, *.csproj test SDK refs), CI workflow steps that run tests, the OS/runtime matrix, coverage tooling and any configured threshold, presence of contract/integration/e2e suites versus unit-only, use of testcontainers or a real DB fixture versus mocking libraries, whether tests are a required status check, and the test-to-source file ratio. If tests are absent or the CI runs them without failing the build, that absence is itself the finding to put to the user, not a gap to fill by asking an open question.

**Example question.**

> Your CI runs pytest on ubuntu+windows across Python 3.11-3.13 and fails the build on any failure; there are 214 test files, no coverage threshold configured, and integration tests use a real SQLite file rather than mocks. Recommended principle: every behavioral change MUST ship a test in the same change, the matrix MUST stay green, and mocked persistence MUST NOT replace the real store. Should this be MUST (blocks the plan) or SHOULD (advisory only, with no downstream enforcement)?

**Example principle.**

```markdown
### II. Test-Backed Change (NON-NEGOTIABLE)

- Every change to observable behavior MUST add or update an automated test in the same change. A plan MUST NOT list manual verification as the only evidence for a functional requirement.
- The full suite MUST pass on every cell of the CI matrix (ubuntu + windows x Python 3.11/3.12/3.13). Skipping or xfailing an existing test to land a change is forbidden.
- Tests that exercise persistence MUST use the real store; a mocked repository MUST NOT be substituted to avoid a fixture.
- No test MAY make a real outbound network call; HTTP MUST be stubbed.

**Rationale:** The offline guarantee and the breadth of the support matrix are only sustainable if the suite is the gate rather than a report.
```

#### Architecture and complexity limits

*Scope: always ask*

**Why it matters.** This is the category the Spec Kit gate machinery was literally designed around — the documented gate examples are "Using <=3 projects?" and "Using framework directly? Single model representation?" A numeric or structural limit here is the most reliably checkable principle a project can own, and it is the one that most often stops an agent from over-building. The structure is inferable; the LIMIT is a human decision and cannot be inferred.

**Inferable from repo.** High for the current shape, zero for the intended ceiling. Detect the number of build/deploy units (solution projects, packages, services, compose services, Dockerfiles), directory layering and its consistency, existing architecture tests (ArchUnit/NetArchTest/import-linter/dependency-cruiser configs), interfaces with exactly one implementation, wrapper/repository/adapter layers over framework types, module dependency direction and any existing cycles, and the count of DI registrations. Report the measured numbers back and ask the user to convert the current shape into a ceiling.

**Example question.**

> The repo has 3 deployable projects, a consistent commands/ (CLI surface) vs plain importable modules split, and no wrapper types over the framework. Recommended limit: plans MUST NOT add a 4th deployable unit or introduce an abstraction layer over a framework API without a written justification. Is 3 the right ceiling, or do you already know a 4th unit is coming?

**Example principle.**

```markdown
### IV. Bounded Structure, No Speculative Abstraction

- An implementation plan MUST NOT create a 4th deployable unit. Adding one requires an entry in Complexity Tracking naming the rejected in-process alternative.
- Framework and library APIs MUST be used directly. A repository, adapter, or facade layer over a framework type MUST NOT be introduced until two concrete callers exist in the codebase.
- An interface or base class with exactly one implementation MUST be deleted rather than retained for future flexibility.
- CLI-surface modules MUST NOT contain business logic; orchestration MUST stay importable and testable without the CLI framework.

**Rationale:** Every speculative seam is paid for on every future read, and the agent will build one whenever the constitution does not forbid it.
```

#### Technology and dependency boundaries

*Scope: always ask*

**Why it matters.** It is the first thing users volunteer unprompted, it is the cheapest area to infer with near-certainty, and left unstated it is the most common cause of an agent quietly introducing a new library or a preview runtime. Stated as a boundary rather than a description ("MUST stay on X, MUST NOT introduce Y") it becomes a clean plan-time gate; stated as a stack list it is overview prose that the evidence says agents do not benefit from.

**Inferable from repo.** Near-total. Read manifests and lockfiles (pyproject/requirements, package.json, *.csproj, go.mod, Cargo.toml), pinned language/runtime/LTS targets, the dependency count and its trend in git history, renovate/dependabot config, any vendored or air-gapped constraints, license constraints from LICENSE and dependency licenses, and the package manager actually in use (lockfile identity). The stack should NEVER be asked; only the boundary — what is frozen, what is forbidden, what the substitution rule is — needs confirmation.

**Example question.**

> You are on .NET 8 LTS with 6 direct runtime dependencies, no preview packages, and Dependabot restricted to patch updates. Recommended principle: stay on the current LTS, and require any new runtime dependency to be justified against the standard library or an already-referenced package in the plan's Complexity Tracking table. Accept, or name specific libraries that are banned or mandatory?

**Example principle.**

```markdown
### V. Dependency Restraint and a Frozen Runtime Floor

- The project MUST target .NET 8 LTS. Plans MUST NOT require a preview SDK, a preview language feature, or a package with a prerelease version.
- A new runtime dependency MUST be justified in Complexity Tracking against the standard library and against every package already referenced. "It is the popular choice" is not a justification.
- Test-only and build-only dependencies are exempt from this rule and MUST NOT be added to the runtime dependency set.

**Rationale:** This project ships to air-gapped environments; every added runtime package is an audit item and a supply-chain surface that someone else has to clear.
```

#### Change safety and workflow gates

*Scope: always ask*

**Why it matters.** This is where a principle acquires a real consequence. A rule with no named enforcement moment — a CI job, a required review, a PR checkbox — is decoration, and the two failure modes of governance documents (drift and unenforceability) both trace back to rules that name no moment of application. It also captures the irreversibility rules (migrations, destructive file operations, data deletion) that are the true "killer items": the steps a competent engineer skips under deadline pressure with the worst consequences.

**Inferable from repo.** High. Read CI workflow triggers and required jobs, branch protection and required status checks (via `gh api`), CODEOWNERS, PR and issue templates, pre-commit/husky hooks, linter and formatter configs and whether they fail the build, the migrations directory and whether down-migrations exist, conventional-commit patterns in git log, release/tag automation, and whether main has direct-push commits in its history. The enforcement mechanism is nearly always already on disk; only the consequence for a violation and the irreversibility rules need confirmation.

**Example question.**

> Branch protection requires a passing lint + test check and one approving review before merge; there are 12 migrations and 4 of them have no down-migration. Recommended principle: PR-only merges with both checks green, plus every migration MUST ship a tested reverse path. The migration half would flag 4 existing files — should it apply to new migrations only, or should the 4 be backfilled?

**Example principle.**

```markdown
### VI. Reviewed, Reversible Change

- Every change MUST reach `main` through a pull request with the lint and test checks green and one approving review. Direct pushes to `main` are forbidden.
- Every new schema migration MUST ship a tested reverse migration in the same change. "Forward-only, restore from backup" MUST NOT be planned. (Applies to migrations added after ratification.)
- Any operation that deletes or overwrites user files MUST be idempotent and MUST be covered by a no-overwrite test before it ships.
- A plan that violates a principle MUST record the violation in Complexity Tracking with the rejected simpler alternative. Silent reinterpretation of a principle is forbidden.

**Rationale:** These are the steps that get skipped under deadline pressure and that cost the most when skipped.
```

#### Governance: enforcement consequence, amendment route, ratification

*Scope: always ask*

**Why it matters.** Mandatory by the template contract and the one place the shipped command already knows it must ask (the ratification date). More importantly it is where the document states its own consequence and its own revision trigger — without both, a constitution drifts out of truth and is ignored rather than amended. It should cost exactly one confirmation, not a discussion.

**Inferable from repo.** Most of it. Ratification date can be proposed from the first commit date or today; the amender can be proposed from CODEOWNERS, the git top committer, or the single-user assumption; the review trigger can be proposed as a default. Version is 1.0.0 on first authoring and follows the existing semver bump rules on amendment. Present the whole block as one pre-filled paragraph and ask for a single yes/edit.

**Example question.**

> Proposed governance block: ratified today; you are the sole amender; amendments require a version bump and a dated Sync Impact Report entry; principles are re-checked when a principle is waived twice in a row or when the stack changes; a MUST violation blocks the plan and must be either removed or justified in Complexity Tracking. Accept as written, or change the amender or the review trigger?

**Example principle.**

```markdown
## Governance

Principles I-VII supersede other practices and are binding gates. The `## Constitution Check` section of the plan template MUST be evaluated against them before Phase 0 and again after Phase 1 design; `/speckit.analyze` treats any conflict with a MUST as CRITICAL. A violation MUST be either removed or recorded in Complexity Tracking with the rejected simpler alternative — it MUST NOT be diluted, reinterpreted, or silently ignored.

Amendments require a version bump per the stated semver rules, a dated Sync Impact Report entry, and approval by the maintainer named here. This constitution MUST be reviewed when the same principle has been waived twice, or when the runtime or deployment target changes.
```

#### Security, privacy, and regulatory compliance

*Scope: conditional*

**Trigger.** Trigger when the repo shows auth, crypto, payment, or PII-handling dependencies; a users/accounts/audit schema; secret-scanning, SAST, or SBOM steps in CI; a SECURITY.md or compliance directory; a regulated-domain signal in README (health, finance, government, education); or when the user names a regime unprompted.

**Why it matters.** When it applies it is non-negotiable and externally imposed, which means the principles write themselves and only need localizing. When it does not apply, asking about it burns a scarce question slot on a hobby project — which is precisely the fatigue the adaptive flow exists to avoid. Note the strong failure mode here: "we must be secure" fails the inversion test outright; only a named boundary (what data, which sink, which helper) is checkable.

**Inferable from repo.** Substantial where it applies. Detect the auth library and flow, secret handling (a secret-store client versus .env reads, gitleaks/secret-scanning config), an existing redaction or masking helper, encryption at rest configuration, PII-shaped columns in the schema or ORM models, CORS/CSP/security-header middleware, dependency-audit and SBOM steps, and SECURITY.md content. Infer the mechanism; ask only which data class is in scope and what the consequence of a violation is.

**Example question.**

> I see a `redact_pii()` helper used in 3 of 11 logging call sites, secrets read from Azure Key Vault in production but from .env in two code paths, and gitleaks in CI. Recommended principle: no user-identifying data in logs, telemetry, or error payloads without the redaction helper, and no .env secret reads outside local development. This would flag the 2 existing code paths — fix them as part of ratification, or scope the rule to new code?

**Example principle.**

```markdown
### VIII. Secret and PII Boundaries

- User-identifying data (email, name, address, IP, free-text notes) MUST NOT reach logs, telemetry, analytics, or error payloads. Any new log or error path that includes a request or response body MUST pass it through `redact_pii()`.
- Secrets MUST be read from the configured secret store at runtime. Reading a credential from an `.env` file outside local development, or committing one in any form, is forbidden.
- Every new endpoint MUST declare its authorization requirement explicitly; relying on a default-allow route is forbidden.

**Rationale:** Log sinks and error trackers are outside the data-retention boundary, so a leak there is not recoverable by deleting a row.
```

#### Inherited external standards (design system, accessibility, organizational policy)

*Scope: conditional*

**Trigger.** Trigger when a design-system or component-library dependency is present; an accessibility linter or axe test is configured; a corporate/government context appears in README, LICENSE, or the org name; a shared org preset or extension is installed; or a linked standards document exists in docs/.

**Why it matters.** When a team is already bound by an external standard, the principles are pre-written and the interview's job collapses to citing and localizing them — which short-circuits several other questions at once. Missing this makes the interview re-derive from scratch what the organization has already mandated, and produces a constitution the team cannot actually adopt because it conflicts with policy.

**Inferable from repo.** Good coverage of the mechanism, none of the mandate. Detect design-system packages and whether hand-rolled equivalents coexist with them, accessibility tooling (eslint-plugin-jsx-a11y, axe, pa11y) and whether it fails the build, an installed organizational preset or extension, a shared style/lint config extended from an org package, and links to standards docs. Ask only which standard is binding and at what conformance level — that is never in the repo.

**Example question.**

> You depend on the internal design system v4 and have axe configured but not failing the build; I also found 6 hand-rolled modal and date-picker components. Are you bound to a stated conformance level (for example WCAG 2.2 AA) and to design-system components for all new UI? If yes, I will make the hand-rolled components an explicit grandfathered exception rather than 6 CRITICAL findings.

**Example principle.**

```markdown
### IX. Design System and Accessibility Conformance

- Every user-facing view MUST meet WCAG 2.2 AA and MUST be built from design-system v4 components. A plan MUST NOT introduce a hand-rolled modal, date picker, combobox, or form control when a design-system equivalent exists.
- Every new or changed view MUST include an automated axe check in its test plan, and the axe job MUST fail the build.
- The six components listed in `docs/a11y-exceptions.md` are grandfathered; touching one of them MUST include migrating it to the design-system equivalent.

**Rationale:** The conformance level is a contractual obligation, and hand-rolled controls are where every past audit finding came from.
```

#### Public interface stability and breaking changes

*Scope: conditional*

**Trigger.** Trigger when the repo publishes a package (registry metadata, publish step in CI), exposes an HTTP/gRPC API with a schema or spec file, ships a CLI, is consumed by another repo in the same workspace, or has tags/releases and a CHANGELOG.

**Why it matters.** A project with external consumers has a compatibility obligation that no other principle covers, and "what counts as a breaking change here" is exactly the kind of durable, checkable rule that /plan can gate on. A project with no consumers gains nothing from it, and a versioning principle on an internal-only app is pure ceremony — which is why this must be conditional rather than always asked.

**Inferable from repo.** High for surface, none for policy. Detect published package identity and current version, release automation and tagging scheme, CHANGELOG structure and whether breaking changes are already called out, OpenAPI/proto/GraphQL schema files and any schema-diff or contract-test step in CI, CLI argument definitions, deprecation markers already in code, and whether previous majors exist. Ask only for the deprecation window and what the team counts as breaking.

**Example question.**

> You publish `acme-client` on npm at 3.4.1, tag releases, and have an OpenAPI spec but no schema-diff check. Recommended principle: semver on the published API and CLI, with any removal or rename requiring one minor release of deprecation plus a migration note. Is one minor release the right window, and does changing an error code or exit code count as breaking for you?

**Example principle.**

```markdown
### X. Compatible Public Surface

- The published HTTP API and CLI MUST follow semantic versioning. A plan that removes or renames a field, endpoint, flag, exit code, or error code MUST include a deprecation period of at least one minor release plus a migration note in CHANGELOG.md.
- Changing the type or nullability of an existing response field is a breaking change and MUST be treated as one.
- Breaking a published consumer to simplify internal code is forbidden; the internal change MUST be adapted behind the existing surface instead.

**Rationale:** Consumers upgrade on their own schedule and cannot be coordinated, so the cost of a break lands entirely outside this repo.
```

#### Operational envelope: performance budget and observability

*Scope: conditional*

**Trigger.** Trigger when the repo has benchmarks or load tests, an SLO/SLA document, APM or structured-logging instrumentation, a serverless/edge/embedded/offline target, an explicit startup-time or bundle-size budget, or a performance-labelled issue history. Skip entirely for CLIs and internal tools with no stated constraint.

**Why it matters.** Performance and observability principles are worthless as adjectives ("fast", "scalable", "observable" are the canonical vague-adjective failures) and excellent as numbers with a named measurement method. When a project has a real latency, memory, or startup constraint, a numeric budget is the single most checkable principle it can own. When it does not, this area produces the most convincing-looking filler in the whole taxonomy, so it must stay conditional.

**Inferable from repo.** Moderate. Detect benchmark suites and any thresholds already asserted, bundle-size or startup-time budgets in build config, caching layers and configured TTLs, pagination helpers and whether any list path lacks them, timeout and retry configuration on outbound calls, the logging library and whether logs are structured, correlation-id propagation, and health/metrics endpoints. The current numbers can often be measured; the BUDGET — the number that must not be exceeded — is always a human decision.

**Example question.**

> Your benchmark suite reports p95 read latency of 180 ms on the seeded dataset, logs are structured JSON with a correlation id, and 3 of 9 list endpoints have no pagination. Recommended principle: p95 read latency MUST stay under 300 ms on that benchmark and every list endpoint MUST paginate. Is 300 ms the budget you would actually defend, and should the 3 unpaginated endpoints be fixed now or grandfathered?

**Example principle.**

```markdown
### XI. Measured Latency and Bounded Queries

- p95 latency on the read path MUST stay under 300 ms against the seeded benchmark dataset, measured by `make bench`. A plan that adds a synchronous outbound call to the read path MUST state its expected budget impact.
- Every list endpoint MUST paginate with a maximum page size of 200. An unbounded query or an unfiltered full-table scan MUST NOT ship.
- Every outbound call MUST set an explicit timeout; relying on the client library default is forbidden.
- Every request path MUST emit a structured log line carrying the correlation id. Unstructured `print`/`console.log` MUST NOT ship in request paths.

**Rationale:** Latency regressions arrive one 20 ms call at a time and are invisible without a stated budget and a benchmark that fails.
```

### Stopping rules considered

#### Draft-first, confirm-once (inference-primary)

**Mechanism.** The interview asks nothing before it drafts. It runs a full repo scan across the six always-ask areas plus any triggered conditional areas, writes a complete candidate constitution with every principle pre-filled and every inference labelled with its evidence ("from .github/workflows/test.yml"), and presents it as a numbered list for one review pass. The user replies with edits by number ("drop 3, weaken 5 to SHOULD, add a rule about X"). Only the user's edits generate follow-up questions, capped at 3, and only where an edit leaves a rule uncheckable. Ratification date and amender are proposed, not asked. Hard backstop: exactly two review rounds, then write.

**Pros.** Terminates by construction and is the most direct answer to the exhaustion complaint — the user's total obligation is reading one page and saying what is wrong with it. Rejecting is far cheaper cognitively than generating, and it exploits the brownfield-primary lock fully: for a mature repo, most principles are genuinely discoverable rather than invented ("derived from the patterns the codebase already enforces"). Wall-clock cost is bounded and predictable at roughly 5-10 minutes.

**Cons.** Defaults are extremely sticky — under 5% of users change a pre-filled value — so a user who skims effectively ratifies whatever the scan produced. That is the satisficing failure in its purest form: a complete-looking constitution nobody chose. It is also weakest exactly where the highest-value content lives: negative scope, the enforcement consequence, and any organizational mandate are barely inferable, so a pure draft-first pass will produce a competent but generic document. Mitigation is mandatory: force at least the negative-scope slot to be a real question the draft cannot pre-fill, and require an explicit typed acceptance rather than silence.

#### Slot-coverage primary (the clarify.md pattern)

**Mechanism.** Score every taxonomy area as Confirmed / Partial / Missing against the repo scan. Ask, one at a time in impact order, only into Partial and Missing slots, using recommendation-first phrasing so most answers cost one word. Stop when every always-ask area is Confirmed or explicitly Deferred and no triggered conditional area remains Partial. Backstop: hard cap of 9 questions; at most 3 conditional areas may fire, the rest are ranked by impact x uncertainty and auto-deferred. Any slot left unfilled is reported in a Deferred table with what was assumed for it.

**Pros.** Produces an equally complete constitution for every project regardless of repo quality, and coverage-complete is genuinely checkable here — unlike an open-ended spec, the taxonomy is a small fixed slot set, so "done" has a definition. It reuses machinery the repo already ships and users already recognize, so it needs no new vocabulary. The explicit Deferred table removes the usual cost of early exit: the constitution carries its own uncertainty rather than hiding it.

**Cons.** Interview length varies with repo legibility, which is the opposite of what an exhausted user wants to hear up front — a thin greenfield repo hits the cap while a well-instrumented one finishes in three confirmations. Marking a slot Confirmed from a repo signal is a judgment call the model makes silently, so the same project can get a 3-question or a 8-question interview depending on scan luck. And it still asks into slots where the honest answer is "this area does not matter to us", because coverage does not know what is unimportant.

#### Marginal-gain primary with dual thresholds

**Mechanism.** Before each question, the agent predicts what the answer would change in the working draft. High threshold: if a candidate question would add, remove, or materially rewrite a principle, ask it — even past the nominal budget. Low threshold: if no remaining candidate question would change anything beyond wording, stop immediately, even with slots unfilled. Operational saturation rule: after a base of 4 questions, stop when 2 consecutive answers add no new principle, constraint, or governance rule. Candidate questions are generated as a pool each turn and ranked by how evenly their plausible answers would split the space of possible constitutions; a question whose answer is confidently predictable is skipped and recorded as an assumption. Backstop: hard cap of 9.

**Pros.** Best quality per question of any option, and it is the only rule that can justifiably both truncate and extend — a confused or contradictory user gets the extra question they need, a decisive user finishes in four. It directly encodes "do not ask what you can infer" as a mechanical rule rather than an instruction, since a predictable answer scores near-zero gain. It also naturally suppresses the ceremonial questions (ratification date, version bump) that carry no information.

**Cons.** The stop condition depends entirely on the model's own judgment of "material", which is unverifiable and drifts between runs — the same project can get a 4-question or a 9-question interview with no explainable reason, and the user cannot predict the length even roughly. It is the hardest to specify unambiguously in a prompt, and the most likely to fail toward stopping early, because an LLM judging its own draft tends to find it sufficient. Non-reproducibility is a real cost for something teams will re-run and compare.

#### Fixed budget primary

**Mechanism.** Announce a fixed number up front — 7 questions, one at a time, recommendation-first — and ask exactly that many, chosen by ranking all taxonomy areas by impact x uncertainty after the repo scan. Everything below the cutoff is inferred, pre-filled, and listed in a Deferred/Assumed table at the end. The count never changes regardless of repo, project type, or answer quality.

**Pros.** Maximum predictability, which is the exact property the user's complaint is about: they can see the finish line from question one, and progress is legible ("3 of 7"). It is trivially specifiable in a prompt, impossible to get stuck in, and reproducible across runs and projects. It also creates useful scarcity — the user knows slots are limited and self-edits rather than expanding.

**Cons.** It is the worst option on quality per question by construction: it over-asks well-instrumented brownfield repos (burning questions on things the CI config already answers) and under-asks thin or contradictory ones (stopping while a genuinely load-bearing area is unresolved). A fixed count also forces the model to manufacture a 7th question when 4 would have done, and manufactured questions are where filler principles come from.

#### User-declared budget up front

**Mechanism.** The first interaction is a single choice of depth: Quick (3 questions — negative scope, testing level, governance confirmation; everything else inferred), Standard (7 questions across the always-ask areas plus up to two triggered conditionals), or Thorough (up to 12, adding all triggered conditional areas and a per-principle enforcement-mechanism probe). The chosen budget is the primary stop rule; slot coverage determines which questions are spent within it, and unspent areas are reported as Assumed with their inferred values. Backstop: the declared budget is a hard ceiling in every mode.

**Pros.** It makes the termination contract explicit and consensual, which directly addresses the stated complaint — the user is never surprised by a question they did not sign up for, and can pick Quick when they just want a usable v1. It also fits the amendment model: Quick produces a deliberately minimal v1 that later /plan and /analyze runs will pressure-test, and re-running to amend is cheap. Three rounds of five beats one round of fifteen.

**Cons.** It asks the user to size a document they have not seen yet, which is a decision they are badly placed to make — most will pick Quick and then find the constitution too thin to gate anything, or pick Thorough out of diligence and abandon it at question 8. It also adds a meta-question before any real content, which is exactly the ceremony the exhaustion complaint is about, and Quick mode risks producing a three-principle document that /plan cannot build a meaningful gate from.

### Quality checks

Mechanical checks that detect a weak principle, each with the signal that fires it.

| Check | Detectable signal |
| --- | --- |
| Bracket-token scan | Any `[ALL_CAPS_IDENTIFIER]` token remains anywhere in the file. This is not cosmetic: bracket tokens are /converge's runtime signal for "unfilled template, skip constitution checks", while /plan and /analyze have no such carve-out and will gate on the placeholder text. Zero tolerance, blocking. |
| Citable-identifier check | A principle is not a `###` heading directly under `## Core Principles`, or its heading carries no stable short identifier (Roman numeral or number + short name). /converge emits task refs of the form `Constitution II`; a principle that cannot be named cannot be cited, so its violations are untraceable. |
| Literal ALL-CAPS MUST presence | A principle body contains no ALL-CAPS MUST or MUST NOT. MUST is the only enforcement trigger in the pipeline. Also flag lowercase "must"/"should" used normatively — the keywords bind only when capitalized, and lowercase prose creates rules that no extractor will ever pick up. |
| Gate-restatement test | The rule cannot be rewritten, without adding information, as a yes/no question about a specific implementation plan. Test mechanically: try to produce the checkbox ("Does this plan ...?"). If producing it requires inventing a threshold, a file name, or a scope that the principle does not state, the principle is not gateable and /plan will fill the Constitution Check with nothing. |
| Forbidden-alternative test | The principle names no cheaper alternative that it rules out. Detect by attempting to fill the plan's Complexity Tracking columns — Violation / Why Needed / Simpler Alternative Rejected Because. If the third column cannot be filled from the principle text alone, the rule is a preference, not a constraint. |
| Requirements-smell lexicon scan | Presence of any of nine defect classes, ranked with ambiguity and non-verifiability as blocking and the rest advisory: subjective language (user-friendly, clean, elegant, appropriate, reasonable); ambiguous adjectives/adverbs (robust, scalable, efficient, quickly, as needed, properly); non-verifiable terms (maintainable, high quality, well-designed); loopholes (where possible, if practical, generally, as appropriate, when feasible); superlatives (best, most secure); comparatives with no baseline (faster, simpler); vague pronouns with no antecedent; incomplete references (see the standards doc); negative-word ambiguity. |
| Inversion / Enron test | Negate the principle and read it aloud. If no competent, well-intentioned team could defend the opposite ("we write insecure code", "we do not test"), the principle discriminates between nothing and is permission-to-play filler. Companion signal: would a failing, dysfunctional team have written this identical sentence? If yes, cut it. |
| Named-enforcement-moment check | The principle names no artifact or moment where it bites. Require one of four tiers: automated (a named lint rule, CI job, hook, or test), structural (a PR-template item, required reviewer, or Complexity Tracking entry), human gate (a named role at a named moment), or none. Tier "none" is the signal — and an emphatic label (NON-NEGOTIABLE, MANDATORY) on a tier-none rule is the strongest form of it, because the label is a claim the team will learn to discount. |
| Instruction-vs-overview sentence classifier | A sentence describes the repository rather than constraining it — no imperative, no MUST/MUST NOT, present-tense description of stack, structure, or purpose ("the project is a React SPA", "the architecture consists of three layers"). Repository overviews are empirically not helpful to coding agents while still costing context; every such sentence is a defect. The single-line framing preamble above `## Core Principles` is the only permitted exception. |
| Atomic-obligation count (not heading count) | Total count of MUST/MUST NOT/SHOULD clauses across the document, counting each semicolon-separated sub-rule separately, exceeds roughly 25. A 5-principle document with 8 sub-clauses each is a 40-instruction document, and adherence degrades measurably with instruction density regardless of how few headings it has. Report the obligation count alongside the principle count; the principle count alone hides the bloat. |
| Character and principle budget | More than 7 `###` principles (warn) or more than 9 (fail), or total file size above ~6,000 characters excluding the Sync Impact Report comment. 6,000 characters is a hard external limit imposed by at least one agent tool's global-rules file, and the 5-9 range converges independently across every governance-document genre. On overflow, force a swap rather than an append: ask which existing principle the new one replaces. |
| Near-duplicate / distractor detection | Two principles cover overlapping ground (shared subject nouns, shared named tools, one restating a subset of the other's rules). A partially-overlapping principle measurably degrades adherence to its neighbour rather than reinforcing it, so overlap is an active defect, not redundancy. Merge, do not keep both. |
| SHOULD-downgrade justification | A SHOULD appears with no recorded reason for the downgrade. SHOULD is extracted by /analyze and /converge but carries no severity rule anywhere downstream, so it buys zero enforcement. Every SHOULD must be a conscious choice with the harm test answered ("what breaks if someone ignores this? nothing severe") — an unjustified SHOULD is usually a MUST the author was not willing to defend. |
| False-positive / grandfathering estimate | A MUST would flag a large share of existing files, endpoints, or open PRs, and the principle states no grandfathering scope or waiver path. Estimate mechanically where possible (count violating files). Rules that flag most of the codebase on day one train the team to ignore the whole document, not just that rule — the same collapse that kills static-analysis rollouts. |
| Standing-rule vs one-time-decision router | The principle records a choice made once ("we chose Postgres over Mongo", "we adopted hexagonal architecture in 2024") rather than a rule applying to every future change. The constitution amends in place with a semver bump and has no supersede mechanism, so decision history silently consumes the principle budget. Route to an ADR; keep only the forward-binding consequence, if any. |
| Durability and altitude check | Two-sided. Too brittle: the principle pins a specific file path, a specific library version below the LTS floor, or a step-by-step procedure that will be wrong within a year — belongs in the plan, config, or AGENTS.md. Too vague: covered by the smell scan. Test by asking whether the rule stays true after a framework upgrade AND whether a reviewer could decide a violation in ten seconds. |
| Aspiration-versus-evidence check | A principle describes behavior the repo scan found no evidence of (a testing MUST with no test directory, an observability MUST with unstructured logs). Either mark it explicitly as a dated migration commitment with an owner, downgrade it, or cut it — an entirely work-as-imagined constitution produces CRITICAL findings on the first /analyze run and is abandoned. |
| Governance completeness | The `## Governance` section omits any of: the amendment route and approver, the versioning policy, the compliance-review expectation wired explicitly to `## Constitution Check` and /analyze's CRITICAL rule, or the stated consequence of a violation. Also flag a malformed footer: missing `**Version** \| **Ratified** \| **Last Amended**` line, or dates not in ISO YYYY-MM-DD. |

### Open questions

Decisions the research deliberately does not settle. These seeded the map tickets.

1. Grandfathering policy when a new MUST would flag a large share of existing code. Three defensible answers with different costs: scope the rule to new code only (honest but creates two standards and the boundary erodes); ratify it repo-wide and accept a wave of CRITICAL findings as a deliberate backlog (highest integrity, highest risk of the team learning to ignore /analyze); or refuse the principle until the code is fixed (cleanest, but loses the rule the user most wanted). The research establishes that unmanaged false positives collapse adoption; it does not say which of these three the interview should default to.

2. What the interview does when repo evidence contradicts the user's stated aspiration — the classic case being a repo with no tests where the user wants a Test-First MUST. Options: accept it as a dated migration commitment with a named owner; auto-downgrade to SHOULD and tell the user why; or accept the MUST verbatim and let the first /plan run surface the gap. This is a judgment about whether the constitution is a description of reality or an instrument of change, and only the human can decide which this project needs.

3. Whether the interview should end by offering to write a condensed restatement of the principles into AGENTS.md or CLAUDE.md. The boundary research permits it (architectural decisions are explicitly welcome in agent instruction files, and instructions that refer to external resources do not work, so a restatement is arguably necessary); Spec Kit's own model treats agent context files as user-owned and outside its ownership, with only an opt-in extension touching them. The locked decisions are silent. This is a product-boundary call, not a research question.

4. Whether domain vocabulary (ubiquitous language definitions) and product-level mission or vision belong in this fork's constitution. Real published constitutions carry them and teams clearly find them valuable, but they are not mechanically checkable by /plan's gate or /analyze's MUST detection, which puts them in direct tension with the locked content model. Either they are out (and the interview says so and routes them elsewhere), or the content model has a stated exception for a non-gated `## Domain Vocabulary` section.

5. Whether SHOULD-level principles are permitted at all. SHOULD is extracted by /analyze and /converge but has no severity rule attached anywhere downstream, so it produces zero enforcement while consuming context and principle budget. A MUST-only constitution is defensible and simpler to explain; allowing SHOULD gives the user a real middle setting for rules they will not defend as blocking. Both are coherent designs and the research does not adjudicate.

6. Whether the preset ships an amendment mode in addition to first-time authoring, and what triggers it. A targeted re-run ("one principle keeps getting waived, revisit it") is a different interview from authoring v1 and needs its own stop rule and its own semver classification step. Shipping only v1 authoring is a legitimate scope decision; shipping both doubles the surface. Related: whether the interview ever proposes an amendment on its own after a /plan or /analyze run surfaces repeated waivers.

7. Whether the constitution should carry an explicit precedence order or tie-break clause for colliding principles (ship-fast versus coverage floors, simplicity versus observability). Prior art on tenets says order by priority and states that an unordered set gives no way to resolve a conflict; but the Spec Kit template has no precedence field, adding one is net-new structure that no downstream consumer reads, and it costs the user a genuine ranking decision. Worth it or ceremony — the human's call.

8. How the interview behaves when the installed preset stack has no Constitution Check gate — most concretely, when the bundled `lean` preset has replaced both /constitution and /plan and dropped the gate entirely. Options: detect and warn that the principles will not be enforced, refuse to run, or author anyway and stay silent. The output-format and enforcement guarantees the interview relies on hold only on the core stack, and there is no research answer for what to do off it.

9. Whether the resulting document is presented as ratified or as a proposal for team review. One person answers the interview, but a constitution that gates everyone's pull requests is a team commitment. The interview could stamp a ratification date and a version of 1.0.0, or it could emit v0.1.0 marked "proposed" with a review step before the first amendment. This is an organizational question about the user's authority, and the research cannot see it.

## Critiques

### Critique: completeness of the taxonomy

**Verdict.** "Strong mechanics, wrong on a load-bearing factual premise, and incomplete in four categories that its own exemplar proves matter. Not ready to build as specified.\n\nWhat holds up: the forbidden-alternative test is the sharpest idea here and is correctly identified as the anti-platitude filter. The inversion test, the near-duplicate check, the atomic-obligation count over heading count, the standing-rule-vs-ADR router, and the aspiration-versus-evidence check are all real defects with real detection procedures. The stop-rule analysis is honest about each option's failure mode, including its own preferred one. The insight that the character budget is externally imposed and that principle counts hide obligation counts is the kind of detail that separates a design from a wish.\n\nThree things break it.\n\nFirst, the factual error. \"Nothing else reads its content\" is false in this repo: eight commands load the constitution, five of them as ungated soft context. The entire content model is derived from that claim, so the derivation is unsound even where the conclusions happen to be right. The gate-restatement and forbidden-alternative tests should govern admission to the GATED principle set, not to the document - and the fix is small, since the structure already has an overflow valve in its optional free-form sections. Applied correctly, it also resolves two open questions the proposal left open.\n\nSecond, the admission tests do not test what they claim. Gate-restatement asks whether a checkbox can be phrased, not whether it can be ANSWERED from an artifact the pipeline reads. That single omission lets through a whole class of code-review rules wearing MUST - redaction at call sites, xfail bans, timeout requirements, print bans, single-implementation-interface deletion - which will produce unfalsifiable PASS marks in every Constitution Check and zero findings in /analyze. That is the same silent-failure mode the proposal opens by warning against, reintroduced by its own filter. It needs a third test that names the answering artifact: plan section, named CI job, or named human gate.\n\nThird, coverage. Diffing the taxonomy against the ratified constitution sitting in this repo turns up three categories with no slot at all - error and failure semantics, interface consistency grammar, and the support matrix as a product commitment - plus data lifecycle, licensing, deploy-and-rollback, documentation obligations, and agent conduct. That last one is the telling omission: this document is read at runtime by eight agent commands, and the taxonomy has no area governing what the agent itself may do unattended. The taxonomy was clearly derived from human-team governance prior art and never re-derived for an agent-driven pipeline.\n\nOn termination, my honest read is that it terminates but under-promises its cost. The stop rules bound turns; four of the eighteen quality checks demand user decisions after the budget is spent, and three of the example questions are compound. The advertised counts are off by roughly 60 percent when measured in decisions. Fixable by requiring every post-draft check to apply a stated default and log it in the Deferred table rather than ask.\n\nRecommendation: keep the quality checks nearly as-is, add the evidence test as a third admission gate, restore the gated-versus-context distinction now that the consumer set is known, add slots for error semantics, interface consistency, and data lifecycle as always-ask or high-priority conditionals, add licensing and deploy/rollback as conditionals, add an explicit lint-grade route-out category, and re-denominate the budget in decisions."

**Termination risk.** "It terminates on turns and does not terminate on decisions, and the unbounded part is not in the stop rules at all - it is in the eighteen quality checks that run after the draft.\n\nThe stop rules themselves are mostly sound. Options 1, 4, and 5 terminate by construction. Options 2 and 3 have nondeterministic length because the stopping judgment (Confirmed/Partial/Missing; \"would this materially change the draft\") is a silent model call, but both carry a hard cap of 9, so they terminate too. The proposal is honest about this in its own cons. That is not where the risk lives.\n\nThe risk is that every stop rule budgets QUESTIONS while at least four qualityChecks demand USER DECISIONS after the budget is spent, and none of them names a default. The character-and-principle-budget check says outright: \"On overflow, force a swap rather than an append: ask which existing principle the new one replaces\" - an unbudgeted question, and one that arrives at the worst moment, after the user thought they were done. The false-positive/grandfathering check requires a scope decision (repo-wide, new-code-only, or drop the rule) that openQuestions #1 explicitly admits has no default. The aspiration-versus-evidence check requires choosing among dated migration commitment, downgrade, or cut - openQuestion #2 also admits no default. The SHOULD-downgrade check requires a recorded reason for every SHOULD. On a repo with any history, all four fire, and a 7-question interview becomes a 12-decision interview, which is the exhaustion complaint returning through the back door.\n\nCompounding it, the exampleQuestions are not single questions. The testing one asks for a three-clause principle AND a MUST-vs-SHOULD level. The security one asks for a principle AND a fix-now-or-scope-to-new-code decision. The change-safety one asks for a principle AND a backfill-or-grandfather decision. If the budget unit is \"turns\", these are cheap and the count is honest; if it is \"decisions the user must make\", the advertised numbers are off by roughly 60 percent. The proposal never defines the unit, and stop rule 4's whole selling point is that the user can see the finish line - a promise that only holds if the unit is the one being counted.\n\nOne more, specific to stop rule 1: \"exactly two review rounds\" bounds rounds but not volume. A user who replies with fifteen edits generates a second draft that is substantially new, and the rule that \"only the user's edits generate follow-up questions, capped at 3\" then has to decide which three of fifteen ambiguities to resolve, silently dropping the rest.\n\nFix: make the budget a decision budget, not a question budget, and require every post-draft quality check to APPLY a stated default rather than ask. Defaults that work: grandfather to new code with the existing violation count recorded inline; downgrade an unevidenced MUST to a dated migration commitment owned by the interviewee; on budget overflow, drop the lowest-ranked candidate and list it in the Deferred table. Every applied default goes in the Deferred/Assumed table, where the user can reverse it without another round trip. That preserves integrity, keeps the advertised number true, and makes the interview reproducible."

#### Gaps

- **[high] Error and failure semantics (error taxonomy, chained causes, degraded-mode behavior, retry/partial-failure policy)** - This is the clearest exemplar-proven gap. The repo's OWN ratified constitution at C:\Work\spec-kit-for-human-team-v1\.specify\memory\constitution.md carries it as a first-class rule in Principle V ("Errors are explicit and chained... raise with actionable context (offending field/value plus a hint), and use `raise ... from exc`... I/O that can legitimately fail MUST degrade gracefully rather than emit a raw traceback") and again in Principle III ("[red]Error:[/red] + non-zero exit on failure, actionable remediation in messages"). No taxonomy area produces this. Area 10 covers observability, which is about emitting signal, not about what the system does when a call fails. Error policy is durable across framework upgrades, names forbidden alternatives cleanly ("MUST NOT swallow an exception", "MUST NOT return a 200 with an error body", "MUST NOT plan a retry without a bounded attempt count and idempotency key"), and is highly plan-visible: a plan that adds an outbound integration either states its failure mode or does not. It is also the single area where an agent silently does the wrong thing most often (bare except, generic 500, swallowed nulls).

- **[high] Interface consistency grammar for the product's own surface (command/verb vocabulary, output shape, exit codes, JSON-vs-human separation, naming conventions for endpoints or flags)** - Area 9 covers whether the public surface may BREAK; it says nothing about whether a new surface must LOOK like the existing one. Area 8 covers this for UI only, and only when an external design system exists. The repo's own constitution devotes an entire principle to it (III. CLI & User-Experience Consistency: reuse the shared verb vocabulary, mirror the catalog-stack model, `--json` goes to stdout with logging redirected to stderr, non-zero exit on failure). This is the highest-frequency real gate for any CLI, HTTP API, or SDK: nearly every feature plan adds a command, endpoint, or flag, so this principle fires on more plans than testing does. It passes both admission tests trivially ("Does this plan introduce a verb outside {list, add, remove, search, info, update}?" / forbidden alternative = inventing a new verb). A team with no external design system and no published package currently gets no slot for consistency at all.

- **[high] Data lifecycle: retention, deletion, export, backup and restore, and the provenance of non-production data** - Area 7 governs PII at the boundary — which sink, which redaction helper, which secret store. It does not govern how long data lives, whether deletion is real or soft, whether a restore path is ever exercised, or whether production data may be copied into staging and dev fixtures. Those are different rules with different failure modes and different forbidden alternatives ("MUST NOT seed a non-production environment from a production dump", "a soft-delete flag MUST NOT satisfy a deletion request for PII", "every new table holding user content MUST declare a retention period in the plan's data model"). Copying prod data into dev is the single most common real-world privacy incident in small teams, and it is precisely the cheap thing a competent engineer does under deadline pressure — the exact profile area 1 and area 5 claim to target. It is also plan-visible: the plan already produces data-model.md, so a retention/deletion declaration has a natural home. Area 5's trigger conditions would fire for a project with migrations, but its example principle only reaches reverse-migrations.

- **[medium] Dependency licensing and provenance policy** - Licensing is named once, buried in area 4's inferableFromRepo string ("license constraints from LICENSE and dependency licenses"), and then vanishes: area 4's exampleQuestion and examplePrinciple are entirely about version floors and dependency count. It never becomes a question the user is asked. This matters because license policy is the rare constraint that is externally imposed, absolutely checkable, and produces a clean MUST NOT with a named forbidden construct ("MUST NOT add a runtime dependency under AGPL or SSPL", "a vendored source file MUST carry its origin URL and license header"). It is also the constraint most likely to be violated by an agent, which optimizes for the popular package and has no view of license compatibility. For the exemplar repo — MIT-licensed, shipping to air-gapped enterprise consumers — this is a live obligation that area 4 as written will not surface.

- **[medium] Release, deployment, and rollback policy (as distinct from merge policy)** - Area 5 is titled "Change safety and workflow gates" but its scope stops at the merge boundary: PR review, CI checks, migration reversibility. Everything after merge is unclaimed — release cadence, environment promotion order, whether a deploy is atomic, whether feature flags are mandatory for risky changes, what the rollback window is, whether forward-fix or revert is the default, and whether a schema change and the code that depends on it may ship in the same release (the expand/contract question, which the reverse-migration rule does not answer). These are durable standing rules, they name real forbidden alternatives ("MUST NOT deploy a schema change and its dependent code in the same release"), and they are visible in a plan, which is where deployment steps get invented. Rollback is also where irreversibility actually bites: area 5 correctly identifies irreversibility as the killer category and then covers only the database half of it.

- **[medium] Supported platform and runtime matrix as a product commitment** - This appears only as incidental detail inside area 2's testing example ("ubuntu + windows x Python 3.11/3.12/3.13"), which frames it as a property of the CI config rather than a standing promise. The exemplar repo treats it as its own section ("Security & Cross-Platform Constraints: Code MUST run on Linux, macOS, and Windows and on Python 3.11-3.13... do not introduce POSIX-only assumptions without a guarded fallback"). The distinction is load-bearing: the support matrix constrains what a plan may ASSUME (POSIX paths, a shell, a specific browser baseline, a minimum mobile OS), not just what CI runs. Coupling it to testing means a project that drops a matrix cell from CI for cost reasons silently drops the commitment too. Every cross-platform CLI, every browser-facing app with a support baseline, and every mobile project needs this and gets no slot.

- **[medium] Documentation obligations that ship with a change** - Excluded by name in the content model ("Build/test/run commands and repo layout - AGENTS.md"), but that exclusion covers agent-facing setup docs, not the obligation to update user-facing documentation when behavior changes. The exemplar constitution carries it as a workflow gate ("update user-facing docs (README.md, docs/, spec-driven.md) when behavior changes"; "User-facing command groups MUST be documented under docs/reference/"). It is checkable at plan and tasks time — does the plan include a docs task for each user-visible change — which is exactly where /tasks and /analyze can see it. Also covers the ADR obligation the content model itself creates: the model routes one-time decisions to an ADR but never establishes a principle requiring that the ADR be written, so the routing rule has no enforcement.

- **[medium] Agent conduct and provenance: what the coding agent itself may do autonomously, and how machine-generated change is disclosed** - The most surprising omission given the product. This constitution is read at runtime by at least eight agent commands, yet no taxonomy area governs the agent as an actor. The exemplar repo has exactly these rules ("disclose any AI assistance used"; "Slash-command-affecting changes MUST be manually exercised through a coding agent and the results reported in the PR"; "Large or cross-cutting changes MUST be agreed with maintainers before implementation"). Real candidates: files or directories the agent MUST NOT modify (generated code, lockfiles, migrations, secrets, CI config), operations that require human confirmation before execution, whether the agent may add a dependency or run a migration unattended, and disclosure in the PR. These are durable, checkable at plan time ("Does this plan modify a protected path?"), and they are the highest-consequence rules in an agent-driven workflow — yet the taxonomy inherited its shape from human-team governance documents and never asks.

- **[low] Cost and resource ceilings** - Listed for completeness and mostly a non-gap. For the large majority of projects a cost principle is unmeasurable at plan time, changes with pricing rather than with the codebase (failing the durability test), and produces the same convincing filler that area 10 warns about. It becomes real only in two narrow cases: an LLM-calling product where token spend per request is a designable quantity, and a cloud-heavy system with a per-environment budget. If it is added at all, it belongs as one extra trigger condition inside area 10 ("a metered external API, a paid inference provider, or a stated cloud budget"), not as its own area. Do not spend an always-ask slot on it.

#### Weak principles

- **Systemic, across areas 2, 5, 7, and 10** - The largest single defect: many example principles gate on facts that exist only in a code diff, and no consumer in this pipeline reads diffs. /plan fills Constitution Check from a plan; /analyze reads spec, plan, and tasks; /converge reads the same artifacts. None of them see source. Concretely uncheckable by the machinery the proposal names as its whole justification: "Any new log or error path that includes a request or response body MUST pass it through redact_pii()"; "Skipping or xfailing an existing test to land a change is forbidden"; "Every outbound call MUST set an explicit timeout"; "Unstructured print/console.log MUST NOT ship in request paths"; "An interface or base class with exactly one implementation MUST be deleted". Each passes the proposal's own gate-restatement test on paper — you can phrase the yes/no question — but the answer is not derivable from any artifact in the pipeline, so /plan writes an unfalsifiable PASS and /analyze finds nothing. The gate-restatement test is therefore under-specified: it asks whether a checkbox can be WRITTEN, not whether it can be ANSWERED from the plan.
  - Fix: Add a third admission test - the evidence test: name the artifact that answers the checkbox. Three legal answers only: a section of the plan (data model, contracts, technical context, Complexity Tracking), a named CI job or lint rule that fails the build, or a named human gate. A rule whose evidence is "read the code" is a code-review standard and MUST be routed to AGENTS.md or a linter config, not to the constitution. Then restate the diff-time rules as their plan-visible or CI-visible form: "a plan that adds a logging or error path carrying request data MUST name the redaction helper in its design" plus "the gitleaks and redaction lint jobs MUST fail the build".

- **Change safety and workflow gates (VI. Reviewed, Reversible Change)** - "Silent reinterpretation of a principle is forbidden." Undetectable by construction. The checkbox is "Did you silently reinterpret a principle?", and anyone who did will answer no; anyone who did it silently, by definition, left no artifact. It is a rule whose violation is defined by the absence of evidence, so it can never produce a finding. It also duplicates the Governance section, which already states the same thing, triggering the taxonomy's own near-duplicate defect.
  - Fix: Replace with a positive completeness obligation that has an artifact: every principle listed in the constitution MUST appear in the plan's `## Constitution Check` with an explicit PASS, N/A, or a matching Complexity Tracking row. An unlisted or unmarked principle is itself a violation. That is checkable by counting - /analyze can diff the principle list against the Constitution Check list - and it catches the real failure (quiet omission) rather than an unobservable mental act.

- **Inherited external standards (IX. Design System and Accessibility Conformance)** - "Every user-facing view MUST meet WCAG 2.2 AA" is not mechanically checkable and the taxonomy treats it as the model of a pre-written, self-checking principle. WCAG AA is a conformance standard with a large majority of criteria that no automated tool evaluates - axe and similar tools detect roughly a third of AA issues, and none of the judgment-based ones (meaningful alt text, logical focus order, accessible name accuracy, error identification quality). An LLM reading a plan cannot decide it. The clause therefore behaves as an emphatic, unenforceable MUST - precisely the tier-none-with-an-emphatic-label pattern the proposal's own named-enforcement-moment check calls the strongest signal of decoration. It also risks the false-positive collapse the proposal warns about, since every view plan technically violates it until audited.
  - Fix: Split into the checkable and the human halves and label them. Checkable and blocking: design-system components mandatory where an equivalent exists (plan-visible), the axe job MUST fail the build (CI-visible), and every new view MUST list its keyboard-and-focus test in the plan. Human gate with a named owner and moment: the AA conformance claim is verified by a stated manual checklist at release, not at plan time. Keep the conformance level in the rationale as the WHY, not as the MUST.

- **Technology and dependency boundaries (V. Dependency Restraint)** - "It is the popular choice is not a justification." This regulates the prose quality of a Complexity Tracking cell, not the plan. Any author or agent rewrites the same decision as "widely maintained, 40M weekly downloads, reduces our surface" and it passes. The rule has no objective failure condition, so it is a preference wearing a MUST, and it will teach authors to write better-sounding justifications rather than fewer dependencies. The same defect applies to "MUST be justified in Complexity Tracking against the standard library and against every package already referenced" - "justified" names no bar.
  - Fix: Make the obligation structural, not rhetorical: adding a runtime dependency requires the Complexity Tracking row to name the specific standard-library or already-referenced API considered and rejected, and to state an estimated line count for the in-house alternative. A row missing either field fails the check. That is a filled-or-not-filled test an extractor can evaluate; "popularity is not a justification" is not.

- **Operational envelope (XI. Measured Latency and Bounded Queries)** - "p95 latency on the read path MUST stay under 300 ms against the seeded benchmark dataset, measured by make bench." Well-formed and genuinely measurable, but at the wrong moment for this pipeline: /plan cannot predict p95 from a design, so the Constitution Check on this principle is always an unfalsifiable PASS, and /analyze will never find a violation because latency is not a property of spec, plan, or tasks text. The number is real, and it belongs in CI. The taxonomy presents it as the strongest example of a checkable principle, which will lead the interview to produce more principles of this shape - correct numbers, wrong enforcement point.
  - Fix: Separate the budget from the gate. Budget: a named CI job asserts the threshold and fails the build - state it once in Governance or in the enforcement clause, not as a plan gate. Plan gate: the actually plan-visible clause the principle already contains - "a plan that adds a synchronous outbound call, an N+1 access pattern, or an unpaginated list endpoint to the read path MUST state its expected budget impact in Technical Context." Promote that clause to the primary rule and demote the number to its evidence.

- **Architecture and complexity limits (IV. Bounded Structure)** - "An interface or base class with exactly one implementation MUST be deleted rather than retained for future flexibility." Two independent failures. First, invisible to the pipeline: plans do not enumerate interfaces and their implementation counts, so /plan cannot answer the checkbox. Second, the rule is factually wrong for common, legitimate cases - a declared plugin or extension point, a test seam at a process boundary, a public SDK contract - and it will fire on them. The exemplar repo in this very tree would violate it, since its whole architecture is base classes plus a registry designed for third-party extension. A rule that flags the codebase's core design pattern is the false-positive collapse the proposal itself names as fatal.
  - Fix: Scope it to what a plan actually shows and carve out the legitimate case: "A plan MUST NOT introduce an interface, base class, or adapter for a component it describes as having a single implementation, unless that component is a declared extension point listed in <named file>." That is answerable from the plan's component list, keeps the anti-speculation intent, and stops flagging deliberate extension seams.

#### Overreach - belongs elsewhere

- The proposal's stated factual premise is wrong, and it is the premise everything else rests on: "Nothing else reads its content" (only /plan, /analyze, /converge). I verified in this repo that eight commands load the constitution - templates/commands/specify.md:115, clarify.md:71, plan.md:64, tasks.md:68, checklist.md:79, implement.md:93, analyze.md:104, and converge.md:99. Five of those load it as soft governing context with no MUST extraction and no gate. This matters directly for scope: the gate-restatement and forbidden-alternative tests are correct as tests for what belongs in the GATED principle set, but the proposal promotes them to admission tests for the whole document, which cuts content that four real consumers do use. Domain vocabulary, non-goals framing, and error-handling conventions all reach /specify, /clarify, /tasks, and /implement even though /plan cannot gate on them. This also resolves openQuestion #4 (domain vocabulary) in favor of a non-gated section rather than exclusion, and partially answers openQuestion #8: presets/lean/commands/speckit.plan.md:15 does load the constitution - lean drops the Constitution Check gate and the Complexity Tracking table, not the content. The right warning on lean is "your principles will inform but not block", not "your principles will not be read."

- Lint- and config-grade rules that the proposal's own routing logic sends elsewhere, yet its examples model as principles: "Every list endpoint MUST paginate with a maximum page size of 200"; "Every outbound call MUST set an explicit timeout"; "Unstructured print/console.log MUST NOT ship in request paths"; "No test MAY make a real outbound network call; HTTP MUST be stubbed". Each is a single lint rule or a CI setting, each is invisible to every constitution consumer, and each burns part of the ~25-obligation budget the qualityChecks impose. The content model already says standard defaults the agent applies get cut and build/test config goes to AGENTS.md; the examples do not follow it. The qualityChecks need an explicit lint-grade router alongside the existing standing-rule-vs-ADR router - the durability check only catches brittle file paths and versions, not rules that are correct but belong in a config file.

- Restating platform-enforced policy as constitutional text: "Every change MUST reach main through a pull request with the lint and test checks green and one approving review. Direct pushes to main are forbidden." If branch protection is configured, this rule cannot be violated, so it can never produce a finding; if it is not configured, the constitution is not the thing that will stop the push. Either way it buys nothing mechanically while consuming a principle slot in a 5-to-7 budget. Area 5's inferableFromRepo even says the enforcement mechanism is "nearly always already on disk" - the correct conclusion is to cite it in Governance and spend the principle on the part branch protection cannot express, which is the migration-reversibility and irreversible-operation half.

- Self-referential process ceremony in Governance: "Amendments require a version bump per the stated semver rules, a dated Sync Impact Report entry." That is the behavior of the /constitution command itself (templates/commands/constitution.md steps 2 and 4 already do the version bump and the Sync Impact Report unconditionally). Writing it into the document as project policy is the tool documenting its own mechanics inside the artifact it produces. Keep the amender and the approval route - those are real organizational facts the tool cannot know - and drop the bump-and-report mechanics.

- Per-principle repetition of the plan template's contract. Clauses like "Adding one requires an entry in Complexity Tracking naming the rejected in-process alternative" and "A plan that violates a principle MUST record the violation in Complexity Tracking" appear in three different example principles and again in the Governance example. This is one universal rule about how the pipeline handles any violation. Stating it once in Governance and removing it from each principle saves several obligations against the ~25 ceiling and avoids the taxonomy's own near-duplicate defect, which it correctly notes actively degrades adherence rather than reinforcing it.

- Coding-style and naming conventions, which the taxonomy does not exclude and which the exemplar demonstrates it will attract. The repo's own ratified constitution spends a large share of Principle I on `from __future__ import annotations`, underscore-prefixed private modules, `dict[str, Any]` over `Dict`, alphabetical registry ordering, and underscores-in-package-names-hyphens-in-keys. Every one of those is a ruff rule or a review comment; none is visible to any constitution consumer; together they are perhaps a third of that document's obligation budget. The interview will reproduce this pattern on any repo with a strong style guide unless the taxonomy names style as an explicit route-out category alongside build commands and repo layout.

### Critique: enforceability of the example principles

**Verdict.** The structural work is good and the pipeline claims I could verify are accurate: /plan does ERROR on unjustified gate violations ([templates/commands/plan.md](templates/commands/plan.md#L69)), /analyze does hard-code 'Violates constitution MUST' as CRITICAL ([templates/commands/analyze.md](templates/commands/analyze.md#L157)) and does extract 'principle names and MUST/SHOULD normative statements' (L113), /converge does cite principles as `Constitution II` ([templates/commands/converge.md](templates/commands/converge.md#L213)) and does treat a MUST violation as CRITICAL (L170). The gate-restatement and forbidden-alternative tests are the right two filters, and the Single-Tenant example proves they can produce a genuinely enforceable principle. But the proposal has one central defect that runs through nearly every example: it never asks WHICH consumer sees a violation, and the answer is narrow. /plan and /analyze read documents only — spec.md, plan.md, tasks.md, constitution.md — and never touch source. /converge reads code but bounds itself to files named in plan.md and tasks.md plus a keyword search, with an explicit instruction not to infer scope beyond that. Measured against that surface, roughly a third of the clauses in the example principles are inert: CI matrix results, branch protection, lint rules, benchmark outcomes, and repo-wide code archaeology. They pass every filter the proposal defines — they have ALL-CAPS MUSTs, measurable objects, named forbidden alternatives, rationales — and still cannot be violated in any way the pipeline can observe. The proposal preaches 'three consumers, nothing else reads it' and then ships examples that fail its own premise. Two consequences follow. First, the grandfathering apparatus is aimed at a threat that does not exist: an aspirational MUST cannot flag 214 legacy files because nothing reads them, so the architecture is new-work-scoped by construction and openQuestion #1 largely answers itself. Second, the budget is untested against reality — this repo's own constitution is 13,252 characters with 44 MUSTs against a proposed cap of ~6,000 and ~25, so the flagship example flunks the proposed gate by more than 2x. The required change is a per-clause enforcement tier (plan-visible / converge-visible / outside Spec Kit) applied as a third admission test alongside gate-restatement and forbidden-alternative, with 'outside Spec Kit' clauses either cut or explicitly labeled in Governance so the document stops promising enforcement it cannot deliver. Add the missing interface-consistency and data-safety taxonomy areas, reconcile the budget with the dogfood artifact, resolve the marginal-gain cap contradiction, and bound the repo scan. Verdict: sound skeleton, wrong enforcement model, examples not shippable as written.

**Termination risk.** Termination is genuinely fine, and this is the least worrying part of the proposal. Four of the five stop rules terminate by construction: draft-first has a hard two-round backstop, fixed-budget is a constant, user-declared budget is a hard ceiling in every mode, and slot-coverage has a hard cap of 9 with auto-deferral of conditional areas beyond three. No option smuggles in unbounded questioning; every one names a numeric backstop. One real defect: marginal-gain's high threshold says to ask 'even past the nominal budget' while its own backstop says 'hard cap of 9'. Those contradict, and an LLM handed both will follow whichever it read last. State explicitly that the cap wins and that the high threshold only reorders questions inside the cap. A second, subtler risk is not length but a hidden expansion step: 'Only the user's edits generate follow-up questions, capped at 3' in draft-first, plus per-principle enforcement probes in Thorough mode, plus the grandfathering follow-ups embedded in four exampleQuestions ('fix them now or scope to new code?'), plus the SHOULD-vs-MUST probe in the testing example. Each is a real second turn that the announced budget does not count. A user told '7 questions' who answers 12 turns will feel misled even though the flow terminated. Fix by counting turns, not questions, and by making the grandfathering probe unnecessary — which the /analyze finding above largely does, since the pipeline never scans legacy code. Third: none of the stop rules bounds the repo scan itself. Every option opens with a full scan across ten areas — branch protection via `gh api`, dependency licenses, test-to-source ratios, DI registration counts, migration down-file inspection, benchmark thresholds. On a large monorepo that is minutes of tool calls and a large context burn before the first word appears, and the user experiences it as the interview hanging. Cap the scan explicitly: a file/time budget, and a rule that an unresolved signal becomes a question rather than a deeper search.

#### Gaps

- **[critical] The central premise that a MUST creates a repo-wide false-positive wave is factually wrong, and a whole layer of the design is built on it** - I read the actual consumers. [templates/commands/analyze.md](templates/commands/analyze.md#L75-L105) loads spec.md, plan.md, tasks.md and the constitution — it never reads source code. Its Constitution Alignment pass (L135-L138) checks "any requirement or plan element conflicting with a MUST principle", i.e. document text only. [templates/commands/converge.md](templates/commands/converge.md#L136-L142) does read code but explicitly bounds scope to "the file paths named in plan.md and tasks.md, plus a keyword search" and orders "do not infer scope beyond what the artifacts define". So the pipeline is new-work-scoped by construction. An aspirational MUST cannot produce CRITICAL findings on 214 legacy files, because nothing ever looks at them. This invalidates: the closing paragraph of the content model, the 'aspirational MUST does the most damage' argument in the Testing area, the 'False-positive / grandfathering estimate' quality check (its instruction to 'count violating files' has no downstream analogue), the grandfathering offers in three exampleQuestions, and most of openQuestion #1 — which the architecture largely already answers.

- **[critical] No enforcement-tier model: the proposal never distinguishes clauses /analyze can see (document text) from clauses only /converge can see (feature-scoped code) from clauses nothing in the pipeline can see (CI, lint, branch protection)** - The content model asserts three consumers and nothing else, then ships example principles where roughly a third to a half of the clauses are invisible to all three. The 'Named-enforcement-moment check' has a four-tier model but its tiers are about the real world (CI job, PR template, human gate), not about which Spec Kit consumer observes the violation — which is the only tier that matters given the locked framing. Without this, the interview will keep generating clauses that feel enforceable and are inert. Every principle needs each clause tagged: plan-visible / converge-visible / neither.

- **[high] The character and obligation budgets fail against this repo's own dogfood constitution, and the proposal does not acknowledge the conflict** - [.specify/memory/constitution.md](.specify/memory/constitution.md) is 13,252 characters with 5 `###` principles, 44 MUST occurrences and 2 SHOULD. The proposal caps at ~6,000 characters and ~25 atomic obligations. So the flagship, hand-authored example that ships in this repository fails the proposed quality gate by more than 2x on both axes. Either the budget is wrong for real brownfield projects, or the interview must be prepared to tell a maintainer that their existing constitution is a defect. The proposal must pick one and say so; silently shipping a gate the project's own artifact flunks means the first dogfood run produces an absurd result.

- **[high] No taxonomy area covers interface/UX consistency, command-surface coherence, or documentation obligations** - Proven by the repo's own constitution: Principle III is 'CLI & User-Experience Consistency' — verb vocabulary reuse (`list`/`show`/`add`/`remove`), catalog-stack surface mirroring, nesting depth limits, and 'user-facing command groups MUST be documented under `docs/reference/`'. These are highly plan-visible (a plan naming a new command or a new verb is exactly what /analyze reads) and highly durable. The nearest taxonomy area, 'Inherited external standards', triggers only on design-system or a11y dependencies, which a CLI or library never has. A real project's most gateable principle would be silently dropped.

- **[medium] The bracket-token claim is stated as verified mechanism but is not in the code** - The proposal says `[ALL_CAPS]` tokens 'are /converge's runtime signal for unratified template'. [templates/commands/converge.md](templates/commands/converge.md#L87-L88) says only 'If the constitution is an unfilled template, skip constitution checks gracefully' and L129 'From constitution (if not an unfilled template)'. The detection method is left entirely to model judgment; no token syntax is specified anywhere. The quality check is still worth keeping, but presenting an inference as a mechanism means the design's other mechanism claims will not be trusted either. Related: [templates/commands/constitution.md](templates/commands/constitution.md) step 3 explicitly permits 'intentionally retained template slots... explicitly justify any left' — so the core command allows exactly what the proposal declares zero-tolerance. That contradiction needs resolving.

- **[medium] No handling for the fact that /plan's Constitution Check is free-form, so gate quality depends on /plan re-deriving checkboxes every run** - [templates/plan-template.md](templates/plan-template.md#L39-L43) contains literally '[Gates determined based on constitution file]'. There is no gate list, no schema, no persistence. The proposal's gate-restatement test assumes a principle that is restatable as a checkbox will be turned into one — but nothing guarantees /plan produces the same checkboxes twice, and a principle can pass gate-restatement in the interview and still be ignored by /plan. The constitution should therefore state its gates in checkbox-ready form (imperative, one obligation per clause, threshold inline) rather than assume /plan will extract them. That is a content-model requirement the proposal is missing.

- **[medium] No answer for the plan/converge asymmetry on retroactive clauses** - /converge classifies pre-existing code that conflicts with a MUST as `contradicts` -> CRITICAL ([templates/commands/converge.md](templates/commands/converge.md#L152-L171)) whenever that code falls inside the feature's touched scope. So retroactive clauses are not harmless — they bite exactly and only when someone edits a nearby file, which is the least predictable and most annoying moment. Clauses like 'the six components in docs/a11y-exceptions.md are grandfathered; touching one MUST include migrating it' hide a real cost: a one-line bug fix in a grandfathered file now mandates a migration. The interview must surface that trade-off rather than treat grandfathering as free.

- **[medium] Data and state handling — schema/migration semantics beyond reversibility, backup/retention, idempotency of writes — has no home** - 'Change safety' carries one migration clause almost as an aside, yet migrations, destructive file operations and data retention are the highest-consequence, most plan-visible obligations a data-backed project has, and they are exactly what a plan's data-model.md phase produces. The repo's own constitution devotes a whole principle to 'Safe, Idempotent File Operations' (path-traversal confinement, symlink refusal, SHA-256 tracking). Burying this inside a workflow-gates area means it competes with PR policy for one slot and usually loses.

#### Weak principles

- **Testing and verification policy (II. Test-Backed Change)** - Three of the four clauses are unenforceable by any consumer. (a) 'The full suite MUST pass on every cell of the CI matrix (ubuntu + windows x Python 3.11/3.12/3.13)' — this is a CI outcome. /analyze reads three markdown files; /converge reads feature-scoped source. Neither can observe a test run. It is branch protection wearing a MUST. (b) 'Skipping or xfailing an existing test to land a change is forbidden' — a diff-level fact, and /converge only sees current file contents in scope, not what was skipped. (c) 'No test MAY make a real outbound network call' — first, `MAY` is not `MUST`, so by the proposal's own rule it triggers nothing; second, it is a pytest fixture or a lint rule. Only the manual-verification clause is genuinely plan-visible.
  - Fix: Keep the clauses a plan or tasks file can violate in text, and demote the rest. Plan-visible: 'A plan MUST NOT list manual verification as the only evidence for a functional requirement' and 'Every task that changes observable behavior MUST have a paired test task in tasks.md'. Converge-visible: 'Code that persists data MUST be exercised against the real store; a mocked repository MUST NOT be substituted' (converge can see this in the feature's own test files). Move the CI matrix and the no-network rule to AGENTS.md and conftest.py, and if the constitution must mention CI at all, phrase it plan-side: 'A plan MUST NOT add a runtime or platform to the support matrix without adding the matching CI matrix cell in the same change' — that is a plan property and is checkable.

- **Architecture and complexity limits (IV. Bounded Structure)** - 'An interface or base class with exactly one implementation MUST be deleted rather than retained' is repo-wide code archaeology that no consumer performs, and as written it is a standing demand to delete existing code, so it fires as a CRITICAL every time /converge touches a file near a single-impl interface. 'CLI-surface modules MUST NOT contain business logic; orchestration MUST stay importable' fails the measurable-object requirement the proposal itself sets: 'business logic' has no definition, and two reviewers will disagree in ten seconds. 'MUST NOT be introduced until two concrete callers exist' is the strongest clause here but leaves 'wrapper/facade over a framework type' undefined — a reviewer cannot decide whether a thin DTO mapper counts.
  - Fix: Rewrite as forward-binding plan properties with named artifacts. 'A plan MUST NOT introduce an interface, abstract base class, or protocol that has exactly one planned implementation.' 'Modules under `src/specify_cli/commands/` MUST contain only argument parsing and a call to one importable function; a plan MUST NOT place branching, I/O, or state changes there' — name the directory, name the two permitted operations. For the wrapper rule, name the forbidden constructs concretely ('a class whose only members delegate to a single framework object') or replace it with a mechanical check ('a new import-linter contract MUST accompany any new layer').

- **Negative scope (VII. Single-Tenant, Self-Hosted Only)** - This is the strongest example in the set and I could not break its first clause — 'Plans MUST NOT introduce tenant-scoped identifiers on entities, tenant-aware query filters, or a shared control plane' names three concrete forbidden constructs and lands squarely on data-model.md, which /plan produces and /analyze reads. The second clause is weaker: 'Any request implying multiple customer organizations MUST be rejected at spec time, not designed around' relocates the obligation to /specify, which the proposal's own content model says is not a consumer of the constitution. Nothing reads the constitution at spec time, so this clause is inert, and 'implying' is exactly the kind of judgment word the smell scan is supposed to catch.
  - Fix: Drop the second clause or convert it to a plan-side gate: 'A plan whose spec requires isolating data between customer organizations MUST record the conflict in Complexity Tracking rather than design a tenancy model.' Keep the forbidden-construct list verbatim — it is the model the other principles should copy.

- **Technology and dependency boundaries (V. Dependency Restraint)** - Mostly sound, with one silent failure. 'A new runtime dependency MUST be justified in Complexity Tracking against the standard library and against every package already referenced' — the plan template's Complexity Tracking is explicitly conditional: 'Fill ONLY if Constitution Check has violations that must be justified' ([templates/plan-template.md](templates/plan-template.md#L106-L113)). Adding a dependency is not a violation of this principle if it was justified, so a compliant plan has an empty table and there is nothing for /analyze to inspect. The rule as phrased is self-erasing. Also '"It is the popular choice" is not a justification' is unenforceable rhetoric — no extractor evaluates justification quality.
  - Fix: Make the dependency addition itself the violation so the table is actually triggered: 'Plans MUST NOT add a runtime dependency. A plan that must add one MUST record it in Complexity Tracking with the standard-library alternative rejected.' Now the entry is mandatory and its absence is detectable. Delete the 'popular choice' sentence — it is a slogan, not a rule. Keep the LTS floor and the prerelease ban as-is; those are clean plan-visible gates.

- **Change safety and workflow gates (VI. Reviewed, Reversible Change)** - The first clause — 'Every change MUST reach main through a pull request with lint and test checks green and one approving review; direct pushes to main are forbidden' — is branch protection, verbatim. No Spec Kit consumer observes merges, reviews, or check status. The proposal's own exclusion list routes 'build/test/run commands' to AGENTS.md but has no exclusion for repository settings, so this passes every one of its own filters while being pure decoration. 'Any operation that deletes or overwrites user files MUST be idempotent' — 'idempotent' is checkable, but the second half ('MUST be covered by a no-overwrite test before it ships') is the only part any consumer sees, and only when the feature touches such an operation. The last clause instructs /plan to fill Complexity Tracking, which is process, not project policy.
  - Fix: Cut the PR clause entirely — it belongs in branch protection, and stating it in the constitution buys zero enforcement while consuming the obligation budget. Keep the migration clause but make it plan-visible and forward-only: 'A plan that adds a schema migration MUST include a reverse migration and a task that tests it. Forward-only migration MUST NOT be planned.' Rewrite the destructive-write clause with a named construct: 'A task that writes to a path outside the feature directory MUST state its overwrite behavior and MUST have a paired no-overwrite test task.' Move the Complexity Tracking instruction to Governance, where process rules belong.

- **Security and privacy (VIII. Secret and PII Boundaries)** - The clauses are well-formed but their enforcement tier is misrepresented. 'User-identifying data MUST NOT reach logs, telemetry, analytics, or error payloads' and 'any new log path including a body MUST pass it through redact_pii()' are converge-tier only, and only for files inside the feature scope. /analyze will catch this only if the plan text happens to mention logging — most plans do not, so the most important rule in the document is silently the least likely to fire. 'Every new endpoint MUST declare its authorization requirement explicitly; relying on a default-allow route is forbidden' is the strongest clause here because contracts/ is a Phase 1 plan artifact.
  - Fix: Add the plan-visible half so the rule fires at gate time, not only at converge: 'A plan that introduces a new log sink, telemetry export, or error reporter MUST name the redaction path in the plan text.' Keep the redact_pii() clause as the converge-tier backstop and label it as such in Governance. Promote the authorization clause to first position — it is the one that reliably bites at /plan.

- **Design system and accessibility (IX. Conformance)** - 'Every user-facing view MUST meet WCAG 2.2 AA' is not decidable by any consumer, and not fully decidable by any tool — automated checkers cover a minority of the success criteria, so no gate can produce a yes/no on it. It fails the proposal's own gate-restatement test: producing the checkbox requires inventing the measurement method. 'The axe job MUST fail the build' is CI configuration. 'The six components listed in docs/a11y-exceptions.md are grandfathered; touching one MUST include migrating it' pins a file path and a count of six, which the durability check itself calls out as too brittle — the number is stale the first time someone migrates one.
  - Fix: Split the aspiration from the gate. Gate: 'A plan MUST NOT introduce a hand-rolled modal, date picker, combobox, or form control when a design-system v4 equivalent exists' (named forbidden constructs, plan-visible). Gate: 'Every task that adds or changes a view MUST have a paired axe-check task.' Aspiration: state WCAG 2.2 AA once in Governance as the standard the project is bound by, with no MUST, so it does not masquerade as a gate. Replace 'the six components listed' with 'components listed in docs/a11y-exceptions.md' — drop the count.

- **Operational envelope (XI. Measured Latency and Bounded Queries)** - 'p95 latency on the read path MUST stay under 300 ms, measured by `make bench`' is an outcome, not a property of any artifact. /analyze cannot run make bench; /converge inspects code, not benchmark results. This is the single most convincing-looking inert principle in the set, which is exactly the failure mode the proposal warns about and then commits. 'Every outbound call MUST set an explicit timeout' and 'unstructured print/console.log MUST NOT ship in request paths' are both lint rules — ruff, eslint no-console, a custom analyzer — and both are repo-wide facts that converge sees only inside feature scope. 'Every list endpoint MUST paginate' is repo-wide too, though its forward form is fine.
  - Fix: Convert the budget into a plan property, which is the form the principle already half-contains: 'A plan that adds a synchronous outbound call, an N+1 query, or an unindexed filter to the read path MUST state its expected budget impact against the 300 ms p95 target and MUST add a benchmark task.' Now the violation is a missing sentence in plan.md, which /analyze can see. Forward-form the pagination rule: 'A plan MUST NOT introduce a list endpoint without a page-size limit of 200 or fewer.' Send the timeout and print rules to the linter and cite the linter in Governance rather than restating them as principles.

- **Governance block** - The example is the most accurate item in the proposal — it correctly cites [templates/commands/plan.md](templates/commands/plan.md#L69) ('Evaluate gates (ERROR if violations unjustified)') and the CRITICAL rule at [templates/commands/analyze.md](templates/commands/analyze.md#L157). Two defects remain. It claims 'Principles I-VII supersede other practices and are binding gates' without qualification, which is false for every clause I identified above as CI or lint tier — the document promises enforcement it cannot deliver, and that promise is what teams learn to discount. Second, 'MUST be reviewed when the same principle has been waived twice' names no place where waivers are counted; Complexity Tracking lives in per-feature plan.md files and nothing aggregates them, so the trigger can never fire.
  - Fix: State the enforcement tiers honestly: name which principles gate at /plan, which are observed by /converge inside changed files only, and which are enforced outside Spec Kit by a named CI job or linter. A principle whose tier is 'outside Spec Kit' should say so in one clause rather than borrow the authority of the gated ones. Replace the waiver-count trigger with an observable one: 'reviewed when the runtime or deployment target changes, and at each MAJOR release' — dates and releases are observable; uncounted waivers are not.

#### Overreach - belongs elsewhere

- Branch protection restated as policy: 'Every change MUST reach main through a pull request with the lint and test checks green and one approving review. Direct pushes to main are forbidden.' No Spec Kit consumer observes merges, reviews, or check status. This is a GitHub repository setting; writing it in the constitution changes nothing and consumes obligation budget.

A constitution binds future changes. A demand to delete existing code is a backlog item or a one-off cleanup task, and via /converge's `contradicts` classification it will fire unpredictably whenever an unrelated feature touches a nearby file.

- Instructions aimed at the tooling rather than at the project: 'A plan that violates a principle MUST record the violation in Complexity Tracking with the rejected simpler alternative. Silent reinterpretation of a principle is forbidden.' This is already hard-coded in [templates/commands/analyze.md](templates/commands/analyze.md#L60) ('not dilution, reinterpretation, or silent ignoring') and in the plan template's Complexity Tracking section. Duplicating pipeline behavior inside the artifact the pipeline reads is circular; it belongs in Governance at most, once.

- Justification-quality rhetoric: '"It is the popular choice" is not a justification.' Nothing evaluates justification text against this sentence. It reads as authority but is a slogan.

- The 'p95 latency MUST stay under 300 ms measured by `make bench`' clause as a gate — the number belongs in the benchmark's assertion and in the plan's Constraints field ([templates/plan-template.md](templates/plan-template.md#L35) already has a Constraints slot with '<200ms p95' as its example). As a constitution MUST it names an outcome no consumer measures.

- Grandfathering machinery generally — the 'count violating files' quality check, the fix-now-or-scope-later probes in four exampleQuestions, and most of openQuestion #1. These implement a policy for an enforcement surface that does not exist, and every one of them costs the user a real turn.

### Critique: termination and scope boundaries

**Verdict.** Reject as specified; the content model is strong and the delivery mechanism is not. Three defects are structural rather than fixable per-item.

FIRST, THE CONTENT MODEL CONTRADICTS ITSELF and nothing adjudicates. Admission criterion (3) requires "at least one measurable object — a number, a named file, a named tool, a named command, or a named forbidden construct." The durability check bans "a specific file path, a specific library version, or a step-by-step procedure that will be wrong within a year." Named files, tools, and commands ARE the perishable things. The example principles show the collision in every direction: `make bench`, `redact_pii()`, `docs/a11y-exceptions.md`, `.NET 8 LTS`, `ubuntu + windows x Python 3.11/3.12/3.13`. Each satisfies criterion (3) and violates the durability check. The design needs a stated hierarchy — something like "name types and constructs, not versions and paths; a named symbol is permitted only when a rename would be caught by the compiler" — and it has none. Every principle the interview produces will sit on this fault line.

SECOND, IT FAILS ITS OWN CHECKS AGAINST THIS REPO'S OWN CONSTITUTION. `.specify/memory/constitution.md` is 13,252 characters — about 11.4k after excluding the Sync Impact Report comment, which the budget check exempts — against a stated hard fail at ~6,000. It carries at least 41 lines containing MUST across 5 principles, roughly 2.5x the ~25 atomic-obligation cap. It puts binding MUSTs in `## Security & Cross-Platform Constraints` and `## Development Workflow & Quality Gates`, which are `##` not `###`, so under the citable-identifier check those MUSTs are uncitable — /converge cannot emit `Constitution II` for them, yet /analyze will still rate a conflict CRITICAL. The proposal blesses that escape hatch as an "overflow valve", which makes the principle-count check trivially gameable while doing nothing about the character cap. So either the reference artifact this project ships and dogfoods is wrong, or the budget is wrong. The proposal never looks at it. Any design that would hard-fail its own repository's ratified constitution owes an explanation.

THIRD, THE TERMINATION ANSWER IS DEFERRED. "Must terminate" is locked, and the deliverable ships five options with an unresolved trade-off. Meanwhile the caps that do exist count agent questions, while the real cost sits in compound sub-decisions, an unbudgeted whole-repo scan, and an 18-check post-authoring pass that is itself an uncapped second interview with no precedence order and no revision limit.

WHAT TO KEEP: the two admission tests (gate-restatement and forbidden-alternative) are the sharpest anti-platitude filter in the document and should survive verbatim. The negative-scope area is correctly identified as the highest-signal, least-inferable content. The false-positive-collapse argument is right and is the proposal's best insight — it just is not applied to the proposal's own example principles, three of which (single-implementation-interface deletion, repo-wide reverse-migration backfill, WCAG on 6 hand-rolled components) would produce exactly the wave of CRITICAL findings it warns against.

MINIMUM CHANGES BEFORE THIS SHIPS: (1) pick one stop rule — Option 4 with a 7-question ceiling, or Option 1 with a mandatory non-inferable negative-scope question and typed acceptance; (2) declare the quality checks non-interactive with a fixed precedence order and a two-pass limit, and make every unfixable finding degrade to a Deferred-table row rather than a question; (3) decide the grandfathering default once, globally, instead of per principle; (4) add an "already enforced by compiler, linter, CI, or branch protection" exclusion router and re-audit all ten example principles through it — roughly a third of the example clauses do not survive; (5) resolve the criterion-3 / durability contradiction with a stated hierarchy; (6) add a preset-stack precondition that detects whether a Constitution Check gate and /analyze actually exist before authoring, and reconcile the zero-tolerance bracket rule with the shipped command's justified-retention contract; (7) reconcile the 6,000-character and 25-obligation budgets with this repo's own ratified constitution, or explain why the dogfood artifact is the counterexample rather than the benchmark.

**Termination risk.** It terminates on the metric it counts, and does not bound any of the three things the exhausted user is actually complaining about. Four uncapped channels, ranked.

(1) STRONGEST FINDING — the 18 quality checks are a second, uncapped interview bolted onto the end of a capped one. At least five checks cannot be resolved without the user: SHOULD-downgrade justification ("every SHOULD must be a conscious choice with the harm test answered"), aspiration-vs-evidence ("mark it as a dated migration commitment with an owner" — the owner and the date are user data), false-positive/grandfathering ("states no grandfathering scope or waiver path" — scope is a user decision), budget overflow ("force a swap: ask which existing principle the new one replaces"), and named-enforcement-moment tier "none" (the check identifies the defect and prescribes no non-interactive resolution). None of these is charged against the question budget. Nothing states that the checks are auto-fix-or-cut, and no revision-pass limit exists. Worse, two checks pull in opposite directions with no stated precedence: fixing a gate-restatement failure means adding thresholds and named objects, which raises the atomic-obligation count toward the ~25 cap and the 6,000-char cap; fixing density means removing sub-clauses, which re-triggers the gate-restatement failure. A revise-until-clean loop over 18 checks with two-sided criteria and no precedence order is not guaranteed to converge, and the proposal never says "at most N revision passes, then ship with a Known Issues note."

(2) The caps count questions, not decisions — the wrong unit. Every `exampleQuestion` in the taxonomy is compound. Testing embeds three sub-rules plus a MUST/SHOULD choice. Change safety asks the migration question and then "new migrations only, or backfill the 4?" Security asks "fix the 2 code paths as part of ratification, or scope to new code?" Public interface asks the window length AND whether error codes count as breaking. Operational asks the budget AND the grandfathering of 3 endpoints. Design system asks the conformance level AND design-system-only AND the 6-component exception. So a 9-question cap is realistically 18-27 discrete decisions. Felt exhaustion tracks decisions.

(3) Grandfathering is an unresolved per-principle multiplier. openQuestions #1 leaves the policy undecided while 5 of the 10 example questions already contain a grandfathering sub-question. If it is resolved by asking, that is up to +1 question per principle (+7 to +10), which blows every cap in every option. If it is resolved by defaulting, the design must state the default — it does not.

(4) The repo scan is unbounded work with no budget and no failure path. `inferableFromRepo` demands, among ~40 signals: `gh api` branch protection (a network call that can fail or need auth — no fallback specified), git-history dependency-count trend, per-file inspection of every migration for a down path, test-to-source ratio, DI registration count, "interfaces with exactly one implementation", "wrapper layers over framework types", `redact_pii()` coverage across every logging call site ("3 of 11"), unpaginated list endpoints ("3 of 9"), hand-rolled-vs-design-system components ("6"), and a p95 number that implies running `make bench`. Several of these are whole-repo semantic analyses with no tool behind them; the model will grep-approximate and present the approximation as a measured count in a recommendation-first question. If the user disputes a number, that is another round. Question termination is not command termination, and the claimed "5-10 minutes" for the draft-first option is not credible for this scan on a large brownfield repo.

Per-option honest worst case:

- Option 1 (draft-first): agent questions <=3, but user obligation is reviewing ~25 atomic obligations over 2 rounds, and "add a rule about X" is free-form generation moved to the user's side of the keyboard. Bounded in questions, unbounded in effort.
- Option 2 (slot coverage): 9 questions x ~2-3 embedded decisions = 18-27, plus grandfathering, plus check remediation. Realistic 20-35 decisions.
- Option 3 (marginal gain): contains an explicit licence to exceed budget ("even past the nominal budget", "a confused user gets the extra question"), so the hard cap of 9 is the only real bound, and the stop condition is self-judged.
- Option 4 (fixed 7): the only option that genuinely terminates as advertised — and the proposal rates it worst on quality.
- Option 5 Thorough: internally inconsistent arithmetic. 10 areas (6 always-ask + 4 conditionals, all of which fire on a typical corporate web app) plus a stated "per-principle enforcement-mechanism probe" (7-10 more) against a 12-question ceiling. The mode cannot cover its own stated content.

Two structural amplifiers. First, the conditional triggers are far too broad to be exceptions: security fires on any auth or crypto dependency; external standards fires on "a component-library dependency" or "the org name in LICENSE"; public interface fires on "ships a CLI" or "has tags and a CHANGELOG"; operational fires on "structured-logging instrumentation" or an "offline target". This repo fires three of four. Only option 2 caps how many conditionals may fire; options 1, 3, 4 cap only total questions, so conditional breadth silently degrades depth everywhere else. Second, the arithmetic collides with the principle budget: 5 always-ask principle areas + 4 conditionals = 9 principles, which sits exactly at the ">7 warn, >9 fail" ceiling with zero headroom. One principle the user volunteers triggers the hard fail and the overflow-swap negotiation — meaning the flow can ask a mandatory question and then ask the user to delete the answer.

Finally: the deliverable does not pick a stop rule. "Must terminate" is locked context, and the proposal ships five options and an unresolved trade-off. A design document that defers the termination decision has not answered the termination question.

#### Gaps

- **[high] No "already machine-enforced elsewhere" router in the exclusion rules** - The content model has routers for values, overview prose, one-time decisions, build commands, and feature requirements — but no rule that removes a candidate because a linter, the compiler, branch protection, or a required CI check already blocks it. This is the highest-volume filler source in exactly the brownfield case the design targets, because `inferableFromRepo` explicitly harvests CI workflows, branch protection via `gh api`, lint configs, hooks, and manifests, and the example principles then restate those findings as MUSTs. Verified in this repo: `.specify/memory/constitution.md` already carries `markdownlint-cli2 MUST pass`, `MUST pass ruff, pytest (full matrix), CodeQL`, and `_`-prefixed private module naming — all of which the toolchain enforces without the constitution. The missing router is the single fix that would collapse most of the overreach list.

- **[high] No agent-conduct policy, in a constitution whose only readers are agents** - The locked context is a Spec Kit constitution consumed by /plan, /analyze, and /converge. Nothing in the ten areas covers what the agent itself may do: whether it may delete or weaken an existing test to make a change land, rewrite an applied migration, edit generated or vendored files, touch `.specify/`, run destructive shell commands, or commit and push. This project treats that as first-class everywhere else — every shipped command in `templates/commands/` carries a `## Scope Guard` block, and `presets/lean/commands/speckit.constitution.md` is 1,367 bytes of which roughly half is Scope Guard. A constitution for an agent-driven workflow with no agent-conduct principle omits the one category of rule that is both plan-checkable and specific to this pipeline.

- **[high] No preset-stack detection, and no account of composition with `constitution-sync`** - The proposal asserts "/plan, /analyze, /converge — nothing else reads its content." That is false when `presets/constitution-sync` is installed: it declares `strategy: "wrap"` over `speckit.constitution` and propagates amended guidance into `plan-template.md`, `spec-template.md`, `tasks-template.md`, and installed command files. Two concrete consequences the design never addresses. (1) A guided, interactive, multi-round interview wrapped as `{CORE_TEMPLATE}` by a preset that appends a post-pass is a composition hazard — the wrapper's propagation step runs after an interview that may still be mid-negotiation over a budget-overflow swap. (2) `presets/lean` replaces `speckit.plan` with a command that loads `.specify/memory/constitution.md` but never fills any Constitution Check, and ships no /analyze or /converge of its own, so whether anything enforces the authored principles is preset-dependent. The proposal lists this as open question #8 and then builds the whole content model on guarantees it never checks for.

- **[medium] No precedence or tie-break rule for colliding MUSTs** - With 7-9 MUST-bearing principles spanning simplicity, testing, latency, dependency restraint, and accessibility, plan-time conflicts are the normal case, not the exception (a latency budget pushes toward a cache layer; the bounded-structure principle forbids the speculative seam). /analyze's rule is "conflicts with a MUST are CRITICAL" with no arbitration, so a plan that must violate one of two principles is CRITICAL either way. The proposal lists this as open question #7 and leans toward "ceremony". It is not ceremony when the same document instructs a downstream consumer to treat every conflict as blocking.

- **[medium] No documentation and changelog obligation on behavior change** - "What must be updated when observable behavior changes" is durable, project-wide, plan-checkable, and non-standard per project — the exact profile the taxonomy claims to select for. It appears nowhere across the ten areas. This repo's own constitution carries it (`User-facing command groups MUST be documented under docs/reference/`), which is direct evidence that a real authoring pass produces this content and the taxonomy would have suppressed it.

- **[medium] No cost, quota, or model-call budget for LLM- or cloud-heavy projects** - The operational area covers latency, pagination, timeouts, and logging, but not per-request cost or token budgets, or rules like "no synchronous model call in the request path". For the class of project most likely to be running Spec Kit, this is the numeric, plan-checkable constraint with the highest real consequence, and the area's own trigger list (benchmarks, SLO doc, APM, serverless target) would not fire on it.

- **[low] No rule for data retention, deletion, or restore** - The security area is scoped to secrets, PII in logs, and endpoint authorization. "User data MUST be deletable within N days", "backups MUST be restore-tested", and "MUST NOT copy production data into a non-production environment" are durable, externally-imposed, and gateable at plan time. They are also the rules whose violation is unrecoverable — the same argument the proposal uses to justify the irreversibility content in change safety.

#### Weak principles

- **Testing and verification policy** - "The full suite MUST pass on every cell of the CI matrix (ubuntu + windows x Python 3.11/3.12/3.13)" is not a statement about a plan. Apply the proposal's own gate-restatement test and you get "Does this plan make the suite pass on all six cells?" — unanswerable before implementation, so /plan can only ever tick it vacuously. It also pins a runtime matrix that changes when 3.14 lands, violating the design's own durability rule in its flagship example.
  - Fix: Move the matrix assertion to CI, where it already lives, and state the design-time obligation instead: "A plan MUST NOT introduce a platform-conditional code path, a POSIX-only assumption, or a version-gated API without a guarded test covering the other supported cells." That is answerable from a plan document.

- **Architecture and complexity limits** - Two failures in one principle. (a) "A repository, adapter, or facade layer MUST NOT be introduced until two concrete callers exist in the codebase" is unevaluable at plan time — a plan describes code that does not exist yet, so it has zero concrete callers by construction, and "framework type" is undefined. (b) "An interface or base class with exactly one implementation MUST be deleted rather than retained" is a repo-wide refactor mandate, not a plan gate, and on any conventional .NET or Spring codebase it flags every DI-registered service interface on day one. That is precisely the false-positive collapse the proposal spends a paragraph warning about, committed in its own example.
  - Fix: Replace (a) with a named forbidden construct, which the proposal's own criterion (3) demands and this example fails to supply: "Plans MUST NOT wrap `DbContext`, `HttpClient`, or `ILogger` in a project-defined abstraction." Delete (b) or restate it as forward-binding only: "A plan MUST NOT introduce an interface with a single planned implementation."

- **Operational envelope: performance budget and observability** - "p95 latency MUST stay under 300 ms ... measured by `make bench`" cannot be checked against a plan — restated as a checkbox it becomes a prediction, not a verification. It also pins a Makefile target name, which the durability check bans, and the observability bullets ("MUST emit a structured log line carrying the correlation id", "unstructured print/console.log MUST NOT ship") are per-file coding style enforced by a lint rule.
  - Fix: Keep the number as a CI benchmark threshold, and keep only the one clause that a plan can actually be judged against: "A plan MUST NOT add a synchronous outbound call, an unpaginated list query, or an N+1 access pattern to the read path." Route the logging bullets to the linter.

- **Negative scope and forbidden alternatives** - "Any request implying multiple customer organizations MUST be rejected at spec time, not designed around" fails on two counts: "implying" is a judgment word with no object, and it addresses /specify, not /plan — the Constitution Check runs over a plan, which never contains "a request". The structural half of the principle is good; this bullet is the platitude the area exists to exclude.
  - Fix: Cut the bullet and keep the structural rule alone, which is greppable and plan-checkable: "Plans MUST NOT add a tenant or organization identifier to any entity, a tenant-scoped query filter, per-tenant configuration, or a shared control plane."

- **Technology and dependency boundaries** - "'It is the popular choice' is not a justification" is rhetoric with nothing to check. And "a new runtime dependency MUST be justified ... against every package already referenced" is unbounded work that scales with the dependency count — at 6 packages it is tedious, at 60 nobody performs it, so the rule is dead on arrival and the Complexity Tracking cell gets filled with boilerplate. Separately, "MUST target .NET 8 LTS" contradicts the area's own guidance that "the stack should NEVER be asked" and will block the LTS upgrade it should permit.
  - Fix: Replace both with a number, which the proposal says it wants and did not use here: "The direct runtime dependency count MUST NOT exceed 8. Raising it requires a Complexity Tracking entry naming the standard-library alternative rejected." Drop the version pin; keep only "no prerelease or preview packages", which is durable.

- **Governance: enforcement consequence, amendment route, ratification** - "This constitution MUST be reviewed when the same principle has been waived twice" names a trigger no component can evaluate. Waivers are Complexity Tracking rows inside per-feature `specs/###-feature/plan.md` files; nothing aggregates them, nothing counts them, and neither /analyze nor /converge reads across features. It is an unimplementable condition stated as a MUST, in the section whose job is to state real consequences.
  - Fix: Tie the review to an event that actually occurs and is observable: "MUST be reviewed when the runtime or deployment target changes, and at each MAJOR release of this document." If waiver-counting is wanted, it needs a real aggregation step, which is net-new machinery the proposal does not propose.

- **Inherited external standards (design system, accessibility)** - "The six components listed in `docs/a11y-exceptions.md` are grandfathered" commits the exact defect the proposal's own smell lexicon defines as blocking — "incomplete references (see the standards doc)". An extractor reading the constitution cannot resolve which six components are exempt, so /analyze sees an exemption it cannot apply and will flag the grandfathered components anyway. The file path also violates the durability rule.
  - Fix: Name the six component types inline in the principle, or drop the exemption and scope the rule to new code: "Views added or changed after ratification MUST use design-system components." An exemption that lives outside the document does not exist as far as the pipeline is concerned.

- **Change safety and workflow gates** - "A plan that violates a principle MUST record the violation in Complexity Tracking. Silent reinterpretation of a principle is forbidden" is a verbatim restatement of the Governance section's authority clause, inside a numbered principle. The proposal's own near-duplicate check calls partial overlap "an active defect, not redundancy" that "measurably degrades adherence to its neighbour" — and its own example ships the duplicate. Separately, "any operation that deletes or overwrites user files MUST be idempotent" leaves "idempotent" undefined for a delete (does the second call succeed silently or error?), which is the non-verifiability the smell scan blocks on.
  - Fix: Delete the meta-rule from the principle; it belongs only in Governance. Restate the file rule with an observable postcondition: "An operation that deletes or overwrites a file MUST verify a recorded SHA-256 before writing and MUST NOT overwrite an unrecorded file; a no-overwrite test MUST ship with it."

#### Overreach - belongs elsewhere

- Change safety — the PR and branch-protection clauses. "Every change MUST reach `main` through a pull request with the lint and test checks green and one approving review. Direct pushes to `main` are forbidden" is a verbatim restatement of GitHub branch protection, which the area's own `inferableFromRepo` admits is "nearly always already on disk". It is also an unfalsifiable gate: a plan document cannot push to main, so the Constitution Check box passes for every plan ever written. That is the proposal's own inversion-test failure wearing a different costume — a rule compatible with every possible plan is not a rule. Destination: branch protection settings and CONTRIBUTING.md. What legitimately survives in this area is only the irreversibility content (reverse migrations, idempotent destructive file operations), which is a genuine plan-time design decision. The area should be renamed "Irreversibility and destructive operations" and the workflow content deleted.

- Testing — the CI matrix and network clauses. "The full suite MUST pass on every cell of the CI matrix (ubuntu + windows x Python 3.11/3.12/3.13)" is a required status check restated in prose, and it is date-perishable in exactly the way the proposal's own durability rule forbids. "No test MAY make a real outbound network call; HTTP MUST be stubbed" is a `pytest-socket` / handler-level configuration, enforced once. Destination: `.github/workflows/*.yml` and the test config. The area itself is the strongest in the taxonomy — but only for the two clauses no tool can check: "mocked persistence MUST NOT substitute for the real store" and "a plan MUST NOT list manual verification as the only evidence for a functional requirement."

- Technology and dependency boundaries — the version pin. "The project MUST target .NET 8 LTS" is in the `.csproj` and enforced by the compiler; a plan requiring .NET 9 does not build. It is also self-contradictory: the area states "the stack should NEVER be asked; only the boundary", then puts the stack in its own example principle. Worst, it inverts on schedule — when .NET 8 leaves support the constitution blocks the upgrade it should mandate. Destination: the manifest and AGENTS.md. Keep only the substitution rule and the no-prerelease rule, which are durable plan-time judgments.

- Operational envelope — the observability half. "Every request path MUST emit a structured log line carrying the correlation id" and "unstructured `print`/`console.log` MUST NOT ship in request paths" are per-file coding-style rules with existing lint enforcement (flake8-print, eslint no-console, Serilog analyzers). "Every outbound call MUST set an explicit timeout" should be a configured HttpClient/HttpX default made once, not re-litigated in every plan. Destination: the linter and the DI/client configuration; AGENTS.md if a human needs the reminder. The latency budget and pagination ceiling stay — those are durable numbers.

- Inherited external standards — the component-selection rule. "A plan MUST NOT introduce a hand-rolled modal, date picker, combobox, or form control when a design-system equivalent exists" is a per-feature implementation instruction and is directly enforceable by an eslint `no-restricted-imports` rule against the hand-rolled paths. Destination: the lint config plus AGENTS.md. The WCAG 2.2 AA conformance level and "the axe job MUST fail the build" are legitimately constitutional — externally imposed, contractual, durable.

- Governance as a taxonomy AREA. The proposal itself says the Governance block contains "three things the enforcing consumers do not read" and that it "should cost exactly one confirmation, not a discussion" — then lists it as one of six always-ask areas, which both inflates the apparent policy surface (5 real principle areas, not 6) and invites the discussion the design says to avoid. Destination: a fixed, pre-filled footer step executed outside the question budget, with a single accept-or-edit that is not counted as a question.

- Public interface stability — the semver definition clause. "Changing the type or nullability of an existing response field is a breaking change and MUST be treated as one" is what semantic versioning already means; the proposal's own exclusion rule ("standard, widely-known defaults the agent already applies — cut; the constitution records what is NON-STANDARD") deletes it. "Breaking a published consumer to simplify internal code is forbidden" is a motive-based rule and unfalsifiable — nobody labels their PR that way. What is non-standard and worth one sentence: the deprecation window length, and whether exit codes and error codes count as surface. That is a clause, not a principle-sized block.

- Security — the authorization-default clause. "Every new endpoint MUST declare its authorization requirement explicitly; relying on a default-allow route is forbidden" describes a framework configuration decision (a default-deny fallback policy or a global `[Authorize]` filter) that is made once and then enforced by the framework on every route without anyone re-checking it. By the proposal's own router that is a one-time decision — an ADR plus a line of startup code — not a standing plan gate. The secret-store and PII-in-logs clauses are the real content of this area and they stay.

- Cross-cutting: the zero-tolerance bracket-token check rests on a mechanism that does not exist as described, and contradicts a shipped contract. `templates/commands/converge.md` says only "if the constitution is an unfilled template, skip constitution checks gracefully" — it never specifies bracket-token detection, so "bracket tokens are /converge's runtime signal" is an inference presented as a fact about the pipeline. More concretely, `templates/commands/constitution.md` explicitly permits retained tokens: "no bracketed tokens left except intentionally retained template slots that the project has chosen not to define yet—explicitly justify any left", and lists "follow-up TODOs if any placeholders intentionally deferred" as a normal output. A blocking zero-tolerance rule collides head-on with the command it has to coexist with. Reconcile it or drop the "blocking" label.

## Sweep findings

### How the constitution is produced and consumed in this repo

*Sweep key: `consumption`*

Across official Spec Kit sources, ~10 blog/tutorial write-ups, two real published `.specify/memory/constitution.md` files, and four GitHub issues/discussions, a consistent picture emerges. (1) The official `/speckit.constitution` command is NOT an interview — it fills bracket placeholders in a template and infers missing values from repo context, which is exactly why users report not knowing what to put in the file. (2) The canonical category set comes from the SDD whitepaper's Nine Articles (Library-First, CLI Interface, Test-First, Articles IV–VI project-defined, Simplicity, Anti-Abstraction, Integration-First), and the template's own comments seed Observability and Versioning & Breaking Changes. (3) Real teams cluster into two species: compliance/stack-shaped constitutions (etalab-ia/ai-kit: 15 MUST-principles about EU AI Act, RGAA accessibility, DSFR design system, ProConnect auth, Python-first) and product/domain-shaped constitutions (masonfox/tome: Purpose/Mission/Vision, Non-Negotiables, Domain Vocabulary, Scope Boundaries — categories no official guidance mentions). (4) The recurring category taxonomy across all guidance is: code quality & testing (coverage thresholds, TDD), technology stack constraints, security & compliance, architecture/simplicity/anti-abstraction, documentation, development workflow & gates, governance/versioning — plus the tome-only family of scope boundaries and ubiquitous language. (5) The dominant, well-documented failure mode is platitudes: generated constitutions are "obvious", generic, and non-binding; the sharpest critique is "if a rule is compatible with every possible implementation, it is not a rule." (6) Enforcement is leaky — the plan template has a Constitution Check gate but `/speckit.implement` was reported not to load the constitution at all. (7) Constitutions evolve (ai-kit is at v1.10.0); guidance says spend ~5 minutes, not aim for completeness. (8) Users are documented as confused about the boundary between constitution principles and spec detail. All of this argues for a short, branching, forcing-function interview that produces few, falsifiable, gate-checkable rules — not a long questionnaire.

- **The official /speckit.constitution command does not interview the user. Its execution flow is: load the template, identify [ALL_CAPS] placeholders, then "Collect/derive values for placeholders: If user input (conversation) supplies a value, use it. Otherwise infer from existing repo context (README, docs, prior constitution versions if embedded)." The only mandated question is for the ratification date ("if unknown ask or mark TODO").**
  - *Evidence:* c:\Work\spec-kit-for-human-team-v1\templates\commands\constitution.md#L79-L91 (fork); parity confirmed against upstream at <https://github.com/github/spec-kit/blob/main/templates/commands/constitution.md?plain=1>
  - *Implication:* This is the exact gap a guided interview fills. There is no upstream interview to conflict with or replicate — the interview is net-new behavior layered before the existing fill-the-template step. Design it to produce the same placeholder values the command already expects, so the downstream write step stays unchanged.
- **The stock template offers only five generic principle slots plus two free-form sections and a Governance section. Its inline examples are: "I. Library-First", "II. CLI Interface", "III. Test-First (NON-NEGOTIABLE)", "IV. Integration Testing", and "V. Observability, VI. Versioning & Breaking Changes, VII. Simplicity". Section 2 examples: "Additional Constraints, Security Requirements, Performance Standards"; Section 3: "Development Workflow, Review Process, Quality Gates".**
  - *Evidence:* c:\Work\spec-kit-for-human-team-v1\templates\constitution-template.md#L6-L47
  - *Implication:* The template's own comments are the de-facto category menu most users copy. An interview should either adopt these seven categories as its default question set or explicitly replace them — but it must map answers back to these headings, because the plan template reads this structure.
- **The SDD whitepaper defines the canonical Nine Articles: I Library-First, II CLI Interface Mandate, III Test-First Imperative, IV/V/VI intentionally project-defined, VII Simplicity, VIII Anti-Abstraction, IX Integration-First Testing. It states explicitly: "Articles IV, V, and VI are intentionally defined by each project's constitution rather than prescribed by Spec Kit" and that for one project "Article IV might govern security and access boundaries; for another, it might define integration test requirements."**

### Authoring guidance Spec Kit gives about constitutions

*Sweep key: `upstream-guidance`*

Standing policy documents fail in six recurring, detectable ways, and the evidence base is stronger than the usual platitudes. (1) They decay because they sit outside the work loop: the gap between "work-as-imagined" and "work-as-done" is structural, and documented architecture provably drifts from implemented architecture. (2) Rules become unenforceable through specific, machine-detectable linguistic defects — the requirements-smells literature names nine of them (subjective language, ambiguous adjectives/adverbs, non-verifiable terms, loopholes, superlatives, comparatives, negative words, vague pronouns, incomplete references) and practitioners rank ambiguity and non-verifiability as the most severe. NASA JPL's Power of Ten deliberately admits only rules a checker can verify; Anthropic's own docs draw the same line ("hooks are deterministic; CLAUDE.md instructions are advisory"). (3) Rule count has hard ceilings on both sides: humans hold ~4 chunks (Cowan), checklists work at 5-9 items (Gawande), and IFScale shows the best frontier models hit only 68% adherence at 500 instructions with a measured bias toward earlier instructions. (4) Context bloat is now empirically grounded: Gloaguen et al. found repository context files do not generally improve agent task success while adding over 20% inference cost — but critically, "instructions in the context files are well followed by coding agents, repository overviews... are not helpful." That single result is the most actionable input to a constitution interview: capture imperative, non-standard instructions; refuse narrative overview prose. Chroma's Context Rot (18 models, all degrade) and Lost in the Middle (U-shaped position curve) add ordering constraints. (5) The opposite failure — vacuous rules — has a clean detector: Enron's stated values were Communication, Respect, Integrity, Excellence (Lencioni), and a principle whose negation nobody would defend cannot discriminate between options. (6) The interview's job is therefore not to elicit principles but to reject them: force each candidate through a checker test, a negation test, a "which two decisions does this settle differently" test, and a hard cap near the template's existing five slots. The repo's own templates/constitution-template.md already defaults to five principle slots plus a version/ratified/last-amended footer — that default is well calibrated and the interview must actively resist growth past it.

- **The gap between written procedure and actual practice is structural, not a discipline failure. Hollnagel's Work-as-Imagined vs Work-as-Done: WAI is "an idealized view of the formal task environment that disregards how task performance must be adjusted to match the constantly changing conditions of work"; things go well "because people make sensible adjustments according to the demands of the situation," not because they follow procedures.**
  - *Evidence:* <https://www.england.nhs.uk/signuptosafety/wp-content/uploads/sites/16/2015/10/safety-1-safety-2-whte-papr.pdf> (Hollnagel, From Safety-I to Safety-II white paper)
  - *Implication:* DETECTABLE SIGNAL: a principle written in the aspirational future tense with no evidence it describes current behavior. VALIDATION CHECK: for each principle, require an answer to "name a decision in the last two weeks where the team already did this." If the answer is empty, mark the principle as ASPIRATIONAL and force it into a dated migration plan with an owner, or cut it. A constitution that is entirely work-as-imagined will be entirely ignored.
- **Coding standards die by leaving the work loop, not by being wrong. Bourgau's analysis of team standards: even completed standards initiatives "often turn into documents that everyone forgets when facing day to day urgencies," and the approaches that survive (async decisions captured in PRs, mob programming) work because the standard is produced and reinforced inside the act of coding rather than beside it.**
  - *Evidence:* <https://philippe.bourgau.net/3-good-and-bad-ways-to-write-team-coding-standards-and-conventions/>
  - *Implication:* DETECTABLE SIGNAL: a principle that names no moment of application. VALIDATION CHECK: every principle must name the artifact and moment where it bites — PR template item, CI job, planning gate, review checklist line, or hook. Flag any principle whose enforcement field is empty or says "team discipline"/"code review will catch it." Reviewers not noticing is the default outcome, not the exception.
- **Documented architecture and implemented architecture provably diverge over time; this is the named phenomenon of architectural erosion and drift (Perry & Wolf 1992), with erosion caused by violating architectural principles and drift caused by insensitivity to them. Architectural knowledge "erodes or even gets lost during the lifetime of a system, and accordingly, the documented and implemented architectures are drifting apart from each other."**
  - *Evidence:* <https://arxiv.org/pdf/2112.10934> (Understanding software architecture erosion: a systematic mapping study); <https://arxiv.org/pdf/2103.11392> (Understanding Architecture Erosion: The Practitioners' Perspective)
  - *Implication:* DETECTABLE SIGNAL: a constitution with no amendment trigger, no owner, and no last-amended date. VALIDATION CHECK: require (a) a version and last-amended date, (b) a named amendment trigger ("when we adopt a new datastore", "every quarter", "when a principle is waived twice"), and (c) an owner per principle. Also flag any principle that restates something already true in code — drift will silently falsify it and the whole document loses credibility with it.
- **Developers dismiss rule systems wholesale once the false-positive rate crosses a threshold. Google's Tricorder experience: "Google developers have a strong bias to ignore static analysis, and any false positives or poor reporting give them a justification for inaction." Google caps analyses shown at review at 10% effective false positives and runs an overall effective false-positive rate just under 5%. Crucially: "Developers, not tool authors, will determine and act on a tool's perceived false-positive rate" — a false positive is any report the developer did not want to see.**
  - *Evidence:* <https://cacm.acm.org/research/lessons-from-building-static-analysis-tools-at-google/>
  - *Implication:* DETECTABLE SIGNAL: a principle that would flag a large amount of existing, accepted code, or that has obvious legitimate exceptions with no stated exemption path. VALIDATION CHECK: ask "how many current files/PRs would violate this?" If the honest answer is "most of them," the principle needs either a grandfathering scope (new code only, this directory only) or a documented waiver mechanism. Otherwise the first wave of noise trains the team to ignore the whole constitution, not just that principle.
- **Believing in a rule does not produce compliance. Johnson et al. interviewed 20 developers and found that although all participants felt static analysis use is beneficial, false positives and the way warnings are presented were barriers to actual use.**
  - *Evidence:* <https://homepages.dcc.ufmg.br/~figueiredo/disciplinas/2019b/ese/paper1joao.pdf> (Johnson, Song, Murphy-Hill, Bowdidge, "Why Don't Software Developers Use Static Analysis Tools to Find Bugs?", ICSE 2013)
  - *Implication:* DETECTABLE SIGNAL: the interview mistaking agreement for adoption. VALIDATION CHECK: never accept "the team agreed to this" as evidence a principle will hold. The interview should not ask "do you agree with X?" (everyone agrees with everything) — it should ask "what happens to a PR that violates X?" A principle whose answer is "nothing" is decoration. Unanimous agreement on a principle is weak evidence it is vacuous, not strong evidence it is good.
- **Unenforceable rule language is machine-detectable. Femmer et al.'s Smella tool detects nine requirements smells in natural language: subjective language, ambiguous adverbs and adjectives, loopholes, non-verifiable terms, superlatives, comparatives, negative words, vague pronouns, and incomplete references — using POS tagging, dictionaries, and lemmatization, achieving ~59% precision and 82% recall on 336 requirements, 53 use cases and 1,082 user stories from three companies. Smells are defined as linguistic violations of the ISO 29148 requirements-quality standard.**
  - *Evidence:* <https://arxiv.org/pdf/2305.07097> (Automated Smell Detection and Recommendation in Natural Language Requirements, describing Femmer et al.'s Smella)
  - *Implication:* DETECTABLE SIGNAL + VALIDATION CHECK, ready to implement: run this exact nine-item lexical scan over every principle. Concretely flag — subjective language ("user-friendly", "clean", "elegant", "appropriate"); ambiguous adjectives/adverbs ("robust", "scalable", "efficient", "quickly", "as needed"); non-verifiable terms ("maintainable", "high quality"); loopholes ("where possible", "if practical", "generally", "as appropriate", "unless otherwise agreed"); superlatives ("best", "most secure"); comparatives ("faster", "simpler" with no baseline); vague pronouns ("it", "this" with no antecedent); incomplete references ("see the standards doc"). This is the single highest-value automated check for a draft constitution.
- **Practitioners rank ambiguity and non-verifiability as the most damaging requirement defects. Interviews with ten experienced practitioners at a large safety-critical company characterising 12 requirements smells found "the smell types perceived as most severe are Ambiguity and Verifiability, while as most frequent are Ambiguity and Complexity."**
  - *Evidence:* <https://arxiv.org/abs/2404.11106> (Characterizing Requirements Smells)
  - *Implication:* VALIDATION CHECK PRIORITY: when the reviewing agent finds multiple defects in a draft, rank ambiguity and non-verifiability findings above everything else (above style, above ordering, above count). Report them as blocking; report the rest as advisory. This gives the review a defensible severity order instead of a flat list.
- **NASA/JPL's Power of Ten rules were designed under the explicit constraint that a tool must be able to check them — e.g. "It must be trivially possible for a checking tool to statically prove that a preset upper bound on the number of iterations of a loop cannot be exceeded." Holzmann's stated motivation was that the mass of existing coding guidelines is inconsistent and full of arbitrary rules that rarely allow tool-based compliance checks. The set is deliberately ten rules, and within two years it became JPL's institutional coding standard for mission-critical flight software.**
  - *Evidence:* <https://spinroot.com/gerard/pdf/P10.pdf> (Holzmann, "The Power of Ten: Rules for Developing Safety Critical Code"); corroborated at <https://en.wikipedia.org/wiki/The_Power_of_10:_Rules_for_Developing_Safety-Critical_Code>
  - *Implication:* DETECTABLE SIGNAL: a principle for which no checker can be described. VALIDATION CHECK: for every principle require a named checker in one of four tiers — (1) automated (linter rule, CI job, hook, test), (2) structural (PR template checkbox, required reviewer, ADR), (3) human gate (named role signs off at a named moment), (4) none. Any principle in tier 4 must be rewritten or demoted out of the constitution. This is the strongest precedent available: the most safety-critical software organisation in the world adopted "tool-checkable or not a rule" as its design constraint, and capped the set at ten.
- **The fitness-function tradition (Ford, Parsons, Kua, Building Evolutionary Architectures) reframes architecture governance as executable: "Instead of hoping someone catches the violation in a code review, you write an automated test that fails on every PR that breaks the rule" — shifting from governance by inspection to governance by rule.**
  - *Evidence:* <https://www.thoughtworks.com/en-us/insights/articles/fitness-function-driven-development> ; <https://nealford.com/books/buildingevolutionaryarchitectures.html>
  - *Implication:* VALIDATION CHECK: for each architectural principle, ask the interviewee to state the fitness function — the assertion that would fail. If they cannot, the principle is a preference. Prompt with concrete forms: dependency/module-boundary tests, build-time budget assertions, coverage floors, latency SLO checks. A constitution should be able to point at real files (ArchUnit/NetArchTest tests, CI config, .editorconfig, lint config) for the majority of its principles.
- **Anthropic's own Claude Code documentation draws the enforceability line explicitly: "Unlike CLAUDE.md instructions which are advisory, hooks are deterministic and guarantee the action happens." It also prescribes the pruning test — "For each line, ask: 'Would removing this cause Claude to make mistakes?' If not, cut it" — and warns "Bloated CLAUDE.md files cause Claude to ignore your actual instructions!" plus the named failure pattern "The over-specified CLAUDE.md ... Claude ignores half of it because important rules get lost in the noise. Fix: Ruthlessly prune. If Claude already does something correctly without the instruction, delete it or convert it to a hook."**
  - *Evidence:* <https://code.claude.com/docs/en/best-practices>
  - *Implication:* DETECTABLE SIGNAL: a principle marked NON-NEGOTIABLE, MUST, or MANDATORY whose only backing is prose. VALIDATION CHECK: flag every emphatic label not paired with a deterministic gate — the label is a lie the team will learn to discount. Second check, straight from the docs: for each principle ask "would removing this cause a mistake?" and "does the agent/team already do this correctly without being told?" If the model already behaves correctly, delete the principle or convert it to a hook. Third, use the doc's own diagnostic in reverse: if a rule is being violated despite existing, suspect document length before suspecting the team.
- **TOGAF's criteria for a good set of architecture principles are explicitly about decidability, not inspiration. Robust: "each principle should be sufficiently definitive and precise to support consistent decision-making in complex, potentially controversial situations." Understandable: "the intention of the principle is clear and unambiguous, so that violations, whether intentional or not, are minimized." Consistent: "strict adherence to one principle may require a loose interpretation of another principle; the set of principles must be expressed in a way that allows a balance of interpretations." TOGAF also requires each principle to carry four components: Name, Statement, Rationale, Implications.**
  - *Evidence:* <https://pubs.opengroup.org/architecture/togaf92-doc/arch/chap20.html> (canonical, now behind SSO; criteria text corroborated verbatim across mirrors including <http://www.mgarythomas.com/architecture/togaf/principles/>)
  - *Implication:* DETECTABLE SIGNAL A: a principle with a statement but no rationale and no implications. VALIDATION CHECK: enforce the four-part shape — name, statement, why (the failure it prevents), and what it costs/forces. A principle with no stated implication has not been thought through. DETECTABLE SIGNAL B (high value, usually missed): no conflict-resolution rule. VALIDATION CHECK: scan for principle pairs that will collide — ship-fast vs coverage floors, simplicity vs observability, autonomy vs consistency — and require an explicit precedence order or tie-break clause. Without one, every conflict resolves in favour of whoever is under deadline pressure, which means the constitution silently stops applying exactly when it matters.
- **Agent instruction-following degrades measurably and predictably with instruction count. IFScale (500 keyword-inclusion instructions, 20 models across seven providers): "even the best frontier models only achieve 68% accuracy at the max density of 500 instructions." Analysis found three distinct degradation patterns correlated with model size and reasoning capability — threshold decay (near-perfect until a critical density, then rising variance; o3, gemini-2.5-pro), linear decay (gpt-4.1, claude-sonnet-4), exponential decay (gpt-4o, llama-4-scout) — plus a measured "bias towards earlier instructions."**
  - *Evidence:* <https://arxiv.org/abs/2507.11538> (Jaroslawicz et al., "How Many Instructions Can LLMs Follow at Once?"); leaderboard at <https://distylai.github.io/IFScale/>
  - *Implication:* DETECTABLE SIGNAL: obligation count, not heading count. VALIDATION CHECK: parse each principle into atomic obligations (each MUST/SHOULD/NEVER clause, each semicolon-separated sub-rule is one instruction) and report the total, not the number of headings — a 5-principle constitution with 8 sub-clauses each is a 40-instruction document. Second check from the primacy-bias finding: order principles by how often they are actually violated, most-violated first. Do not order alphabetically, by author, or by comfort.
- **Human working memory holds about four chunks, not seven. Cowan's 2001 reconsideration proposed the limit is closer to four chunks when rehearsal and long-term memory support are controlled; subsequent reviews corroborated this. Miller's 7±2 "was meant more as a rough estimate and a rhetorical device than as a real capacity limit."**
  - *Evidence:* <https://philpapers.org/rec/COWTMN> (Cowan, "The magical number 4 in short-term memory"); review at <https://journalofcognition.org/articles/10.5334/joc.387>
  - *Implication:* DETECTABLE SIGNAL: more than about seven principles. VALIDATION CHECK: hard-warn above 7 principles and hard-fail above ~10, with the rationale stated in the warning — a set nobody can recite unaided is a set nobody applies unaided. The interview should force ranking under scarcity ("you have five slots; which one does principle six replace?") rather than accepting additions. Note the chunking escape hatch: a principle can carry sub-detail if the sub-detail is inside a linked, on-demand document rather than in the constitution body.
- **Checklist design converges on the same range from the operational side. Gawande's rule of thumb is five to nine items — explicitly framed as the limit of working memory — with checklists focused on "killer items" (the steps easily skipped whose omission is disastrous), and a 60–90 second budget per pause point, after which "the checklist often becomes a distraction ... People start shortcutting. Steps get missed." Independent practitioner writing on enterprise architecture principles lands in the same band: "Five to ten principles is usually enough. Beyond that, people stop remembering them."**
  - *Evidence:* Book notes/summaries of Atul Gawande, The Checklist Manifesto: <https://sive.rs/book/ChecklistManifesto> and <https://grahammann.net/book-notes/the-checklist-manifesto-atul-gawande> (secondary sources, not the primary text); practitioner source: <https://www.eatransformation.com/p/what-do-useful-enterprise-architecture-principles-look-like>
  - *Implication:* VALIDATION CHECK, with a good interview question attached: ask "which of these are the killer items — the ones a competent, well-intentioned engineer would skip under deadline pressure, with bad consequences?" Only killer items belong in the constitution; everything else belongs in a linter, a skill, or a checklist attached to a specific workflow. Also check reading time: if the constitution takes more than ~90 seconds to scan at a decision point, it will not be consulted at that decision point.
- **Repository context files do not reliably help coding agents, and the part that does help is instructions, not description. Gloaguen et al. evaluated coding agents on SWE-bench tasks with LLM-generated context files and on a new collection of 138 real-world tasks from repositories with developer-committed context files: "we find that providing context files does not generally improve task success rates, while increasing inference cost by over 20% on average. This observation holds across different LLMs, coding agents, and for both LLM-generated and developer-committed context files. Specifically, we find that while instructions in the context files are well followed by coding agents, repository overviews, although popular and recommended by model providers, are not helpful. We conclude that while context files are useful for specifying non-standard coding practices, any attempts to improve performance should be rigorously evaluated before deployment."**
  - *Evidence:* <https://arxiv.org/abs/2602.11988> (Gloaguen, Mündler, Müller, Raychev, Vechev, ETH SRI Lab); practitioner writeup with the per-condition deltas (~3% decrease for LLM-generated, ~4% increase for developer-written, 19–22% cost increases) at <https://developer.upsun.com/posts/ai/agents-md-less-is-more>
  - *Implication:* THE MOST ACTIONABLE FINDING FOR AN INTERVIEW DESIGN. DETECTABLE SIGNAL: descriptive/overview prose in a governance doc — "this project is a...", "our architecture consists of...", restated directory structure, restated tech stack. VALIDATION CHECK: classify every sentence as INSTRUCTION (imperative, tells the agent to do or not do something) or OVERVIEW (describes the repo). Cut all OVERVIEW. Second check, from "useful for specifying non-standard coding practices": flag any instruction that states a standard, widely-known default — those cost tokens and buy nothing. The interview should be explicitly hunting for what is NON-STANDARD about this team, and should refuse to record anything a competent outsider would already assume.
- **Long context degrades adherence non-uniformly across every frontier model tested. Chroma's Context Rot study evaluated 18 LLMs and concluded: "LLMs do not maintain consistent performance across input lengths. Even on tasks as simple as non-lexical retrieval or text replication, we see increasing non-uniformity in performance as input length grows." Degradation is not gradual — models hit cliffs. "Even a single distractor reduces performance relative to the baseline," and multiple distractors compound. Separately, Lost in the Middle established a U-shaped curve: performance is highest when relevant information is at the beginning or end of the context and "significantly degrades when models must access relevant information in the middle of long contexts, even for explicitly long-context models."**
  - *Evidence:* <https://www.trychroma.com/research/context-rot> (Hong, Troynikov, Huber) ; <https://arxiv.org/abs/2307.03172> (Liu et al., "Lost in the Middle")
  - *Implication:* DETECTABLE SIGNAL: length and position. VALIDATION CHECK A: total document length is itself a defect — report the constitution's token/word count and warn when it grows, because every added principle degrades adherence to the existing ones (this is the mechanism behind "15 principles is worse than 5," not a metaphor). VALIDATION CHECK B: the distractor result means a near-duplicate or partially-overlapping principle actively harms the others — flag semantic near-duplicates and merge them. VALIDATION CHECK C: never bury the most important principle in the middle of the document; put it first.
- **Anthropic's context-engineering guidance names both directions of the failure. Context is "a finite resource with diminishing marginal returns"; each token depletes an "attention budget"; the goal is to "find the smallest possible set of high-signal tokens that maximize the likelihood of some desired outcome." On calibration ("the right altitude"), avoid both "hardcoding complex, brittle logic" and vagueness that "fails to give the LLM concrete signals for desired outputs" — instructions should be "specific enough to guide behavior effectively, yet flexible enough to provide the model with strong heuristics."**
  - *Evidence:* <https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents>
  - *Implication:* VALIDATION CHECK, two-sided: flag principles at BOTH extremes. Too brittle — encodes a specific file path, a specific library version, or a step-by-step procedure that will be wrong in six months (these belong in code or config, not a constitution). Too vague — gives no concrete signal (covered by the requirements-smells scan). The interview should aim each principle at the middle altitude: a durable constraint with a concrete test. A useful prompt: "state this so it stays true for two years AND so a reviewer can decide a violation in ten seconds."
- **The classic vacuous-values failure has a named exemplar and a named category. Lencioni opens with Enron's stated corporate values from its 2000 annual report — Communication, Respect, Integrity, Excellence — and argues most values statements are "bland, toothless, or just plain dishonest" and "often highly destructive," because "empty values statements create cynical and dispirited employees and undermine managerial credibility." He distinguishes core values from "permission-to-play" values: "A CEO I worked with confused core values with permission-to-play values when he insisted that integrity was a core value of his company." The same failure appears in Rumelt's "fluff" — "restatement of the obvious combined with a generous sprinkling of buzzwords ... which create the illusion of high level thinking" — and in template-style strategy that produces "laundry lists of lofty goals that aren't actionable."**
  - *Evidence:* <https://hbr.org/2002/07/make-your-values-mean-something> (Lencioni, HBR, July 2002); Rumelt material from book notes/summaries of Good Strategy Bad Strategy: <https://jlzych.com/2018/06/27/notes-from-good-strategy-bad-strategy/> (secondary source)
  - *Implication:* DETECTABLE SIGNAL: the permission-to-play principle. VALIDATION CHECK ("the Enron test"): would a failing, dysfunctional team have written this identical sentence in its own constitution? If yes, it is permission-to-play, not a differentiator — cut it. Companion check ("the inversion test", which also catches TOGAF-style motherhood statements): negate the principle. "We write tests" negates to "we don't write tests" — nobody would defend that, so the principle discriminates between nothing and is worthless as written. A principle survives inversion only if a reasonable team could genuinely hold the opposite position (e.g. "we prefer integration tests over unit tests" inverts to a defensible stance, so it carries information). Apply this to every candidate principle.
- **A long principle list is often an artifact of the elicitation process, not of the team's actual constraints. Rumelt's "dog's dinner objectives": "a long list of 'things to do,' often mislabeled as 'strategies' or 'objectives' ... these lists usually grow out of planning meetings in which stakeholders state what they would like to accomplish, then they throw these initiatives onto a long list ... so that no one's feelings get hurt, and they apply the label 'long-term' so that none of them need be done today."**
  - *Evidence:* Book notes/summary of Richard Rumelt, Good Strategy Bad Strategy: <https://jlzych.com/2018/06/27/notes-from-good-strategy-bad-strategy/> (secondary source)
  - *Implication:* DETECTABLE SIGNAL: one principle per stakeholder, and nothing rejected. VALIDATION CHECK: if the interview transcript shows every participant's suggestion made it into the final document, the document is a dog's dinner. Design the interview to require rejection — a fixed slot count, an explicit "what did we decide NOT to make a principle, and why" section, and a forced trade-off question per principle ("what does this principle cost us? what will we be slower at?"). A principle with no stated cost was never actually chosen.
- **GitHub's analysis of over 2,500 agents.md files found the dominant failure is vagueness, and that concreteness beats description: "Most agent files fail because they're too vague"; "One real code snippet showing your style beats three paragraphs describing it"; specify versions ("React 18 with TypeScript, Vite, and Tailwind CSS" not "React project"); and structure boundaries in three explicit tiers — always do, ask first, never do. Named anti-patterns include vague adjectives without context and aspirational language lacking enforcement mechanisms.**
  - *Evidence:* <https://github.blog/ai-and-ml/github-copilot/how-to-write-a-great-agents-md-lessons-from-over-2500-repositories/>
  - *Implication:* VALIDATION CHECK: every principle must carry at least one concrete artifact — a code example, a named command, a named file/tool, or a counter-example of a violation. Flag any principle that is pure prose. Second, structurally useful for a constitution interview: adopt the always / ask-first / never tiering, because it forces the interviewee to say what is genuinely forbidden (the highest-signal content) rather than what is generally nice. "Never" items are the killer items; if a constitution has no "never" list, the interview failed to extract the real constraints.
- **The repo's own constitution template already encodes a five-principle default with a governance section and a version/ratified/last-amended footer, and its example principles are mostly enforceable and concrete (e.g. "III. Test-First (NON-NEGOTIABLE) — TDD mandatory: Tests written → User approved → Tests fail → Then implement"), while the fifth slot's example comment invites drift by suggesting three alternatives at once ("V. Observability, VI. Versioning & Breaking Changes, VII. Simplicity").**
  - *Evidence:* c:\Work\spec-kit-for-human-team-v1\templates\constitution-template.md (lines 4-29 principle slots; lines 43-50 governance and version footer)
  - *Implication:* The five-slot default is well calibrated against every count finding above (Cowan ~4, Gawande 5-9, EA practitioner 5-10, Power of Ten's cap at 10). VALIDATION CHECK: treat five as the target and seven as the warn threshold, and treat the template's fifth-slot comment as a known drift vector — the interview must pick one principle for slot five, not enumerate options. Also note the template has no conflict-precedence field and no per-principle enforcement/owner field; both are the highest-leverage additions the interview could make, since they close the two biggest gaps identified in this research (unenforceable rules and unresolved principle collisions).

### Real-world Spec Kit constitutions and public guidance

*Sweep key: `web-speckit`*

I researched six genres of short governance documents and confirmed every load-bearing quote by fetching the primary page (search snippets alone were not treated as evidence). The strongest finding is a size ceiling that converges across all six genres: Gawande's checklists say 5-9 items and one page, AWS tenets say "no more than 7 tenets, in descending order of priority", working agreements say 5-10, Definition of Done says 6-12 with every item having a clear pass/fail condition, and both ADRs and team charters say 1-2 pages. These numbers likely share a common 7-plus-or-minus-2 lineage rather than being independently derived, but the agreement is strong enough to treat 7 as a hard cap for a constitution. A hard external constraint reinforces it: Windsurf caps a global rules file at 6,000 characters (about 900 words), Cursor caps a rule at 500 lines, and GitHub caps Copilot instructions at 2 pages, so a constitution meant to be portable across agent tools must fit those budgets.

The second strongest finding is the quality test set, and each genre contributes a different cut question. Tenets contribute the inversion test - "To be effective a tenet needs to have an opposite which could be acceptable to an organisation" - which kills truisms like "we should not build unsecure software". RFC 2119 Section 6 contributes the keyword test: imperatives "MUST only be used where it is actually required for interoperation or to limit behavior which has potential for causing harm", and RFC 8174 adds that the keywords bind only in ALL CAPS, which is exactly what makes rules greppable and machine-checkable. Claude Code's guidance contributes the retention test: "For each line, ask: 'Would removing this cause Claude to make mistakes?' If not, cut it." Definition of Done contributes the verifiability test - every item needs a pass/fail condition - plus a stated consequence for violation, which the Scrum Guide makes explicit. Gawande contributes "killer items": keep only the steps most dangerous to skip.

On the boundary question, my initial read was too strong and I corrected it. Agent instruction files do not exclude governance content - the Claude Code include/exclude table explicitly lists "Architectural decisions specific to your project" as something to include. The real boundary is canonicality plus self-containment: the constitution is the source of truth, instruction files carry short restatements, and the restatement is necessary because GitHub's docs say instructions that "refer to external resources" do not work. AGENTS.md is positioned as "a README for agents" holding build steps, tests, and conventions, which is the operational how-to layer, while the constitution holds tool-agnostic non-negotiables. ADRs mark the other boundary: they are immutable point-in-time records that are superseded and never edited, whereas the Spec Kit constitution is amended in place with a semver bump, so the interview must actively route one-time decisions to ADRs or they will fill the item budget. Two repo findings are worth acting on: the constitution command already demands MUST/SHOULD discipline, but only at validation time (templates/commands/constitution.md#L110), and it defines semver bump rules the interview should classify against (#L87-L91).

- **AWS states the tenet count rule directly: "The general rule of thumb is to have no more than 7 tenets, in descending order of priority."**
  - *Evidence:* <https://aws.amazon.com/blogs/enterprise-strategy/tenets-supercharging-decision-making/>
  - *Implication:* Do not just cap the count - make the interview ask the user to ORDER the principles. - **AWS tenets always carry the suffix "unless you know better ones": "Any set of tenets in AWS is followed by the phrase 'unless you know better ones.' It invites debate and an open mindedness on whether one or more tenets remain appropriate."**
  - *Evidence:* <https://aws.amazon.com/blogs/enterprise-strategy/tenets-supercharging-decision-making/>
  - *Implication:* End the interview by asking who can amend the constitution and how, and write that answer into the document. A governance doc with no stated amendment route gets ignored rather than revised. This is a required interview question, not an optional one.

  - *Evidence:* <https://cursor.com/docs/context/rules>
  - *Implication:* Treat 500 lines as an absolute upper bound for anything an agent loads every session, and prefer splitting: if the interview surfaces a large body of detail (a full style guide, a security standard), route it to a separate referenced file and keep only the governing principle in the constitution.
- **Windsurf/Cascade enforces byte budgets, not just advice: global_rules.md is "Limited to 6,000 characters" and workspace rules are "Limited to 12,000 characters per file", with the guidance "Keep rules simple, concise, and specific. Rules that are too long or vague may confuse Cascade" and a preference for bullet points and XML grouping over long paragraphs.**
  - *Evidence:* <https://docs.devin.ai/desktop/cascade/memories> (docs.windsurf.com now redirects here)
  - *Implication:* 6,000 characters is roughly 900 words - this is the hardest external constraint on constitution size and it independently justifies the 5-9 item cap. If the constitution is meant to be portable across agent tools, the interview should enforce a character budget, not only an item count, and warn when the draft exceeds ~6,000 characters.
- **GitHub Copilot's docs require "short, self-contained statements" and list three instruction types that do not work: "Requests to refer to external resources when formulating a response", "Instructions to answer in a particular style", and "Requests to always respond with a certain level of detail".**
  - *Evidence:* <https://docs.github.com/copilot/concepts/about-customizing-github-copilot-chat-responses>
  - *Implication:* Every principle must stand alone. Reject phrasings like "follow our internal style guide" or "see the wiki" during the interview - if the rule lives elsewhere, ask the user to state the one-line version that goes in the constitution. Self-containment is also what makes each principle independently checkable.
- **GitHub's own guidance caps Copilot instruction files at "no longer than 2 pages" and says they "must not be task specific"; the recommended content is project overview, tech stack, coding guidelines, project structure, and available tooling - not per-task prompts.**
  - *Evidence:* <https://github.blog/ai-and-ml/github-copilot/5-tips-for-writing-better-custom-instructions-for-copilot/>
  - *Implication:* Use "not task specific" as a second routing filter alongside the ADR filter: rules about how to do one particular job belong in a command, skill, or prompt file, not in the constitution. The interview should ask "does this apply to every change, or only to a certain kind of work?"
- **AGENTS.md is positioned as "a README for agents: a dedicated, predictable place to provide the context and instructions to help AI coding agents work on your project", holding "build steps, tests, and conventions that might clutter a README or aren't relevant to human contributors" - operational how-to, kept separate so READMEs stay "concise and focused on human contributors".**
  - *Evidence:* <https://agents.md/>
  - *Implication:* Draw the split in the interview output: AGENTS.md answers "how do I build, test, and submit here" (commands, layout, tooling); the constitution answers "what is non-negotiable regardless of tool". If a candidate principle is really a build command, move it to AGENTS.md instead of spending one of the 7 slots.
- **The Scrum Guide defines the DoD as "a formal description of the state of the Increment when it meets the quality measures required for the product", and attaches a hard consequence: an item that does not meet it cannot be released or presented at Sprint Review and returns to the Product Backlog.**
  - *Evidence:* <https://scrumguides.org/scrum-guide.html> (Definition of Done section)
  - *Implication:* A governance doc needs a stated consequence, not just a list of rules. Add an interview question: "what happens when a change violates this - blocked merge, documented exception, or just a note?" Principles with no consequence are decoration, and the answer also determines the MUST/SHOULD keyword.
- **Practitioner DoD guidance gives both a count and a per-item test: "Aim for 6-12 items. Every item should earn its place by preventing a real category of problem"; "Every item should have a clear pass/fail condition" - contrasting "Code is good quality" and "testing done" (unverifiable) with "Code passes static analysis with zero critical issues" (checkable); and warns "Adding items your team routinely skips just trains everyone to ignore the DoD entirely."**
  - *Evidence:* <https://kollabe.com/posts/definition-of-done-checklist> (practitioner blog - lower authority than the Scrum Guide, cited for the item count and the pass/fail phrasing)
  - *Implication:* For each MUST, ask "how would CI or a reviewer catch a violation?" If the user cannot name a check, either rewrite the principle until they can, downgrade it to SHOULD, or cut it. Also warn the user directly that a rule the team routinely ignores damages the whole document.
- **Gawande's checklist rules of thumb: "A rule of thumb some use is to keep it to between five and nine items"; "Ideally, it should fit on one page"; focus on "the killer items - the steps that are most dangerous to skip and sometimes overlooked nonetheless"; and "After about sixty to ninety seconds at a given pause point, the checklist often becomes a distraction from other things. People start 'shortcutting.'" The preferred form is DO-CONFIRM (work from expertise, then pause to confirm) rather than READ-DO (follow like a recipe).**
  - *Evidence:* Atul Gawande, The Checklist Manifesto, as excerpted in Derek Sivers' book notes: <https://sive.rs/book/ChecklistManifesto>
  - *Implication:* The "killer items" test is the best selection prompt for the interview: "which rules have actually been broken here, or would hurt most if skipped?" That anchors principles in real incidents instead of aspiration. The DO-CONFIRM framing also sets the right register for a constitution - it constrains competent engineers at checkpoints, it does not narrate how to do the work.

### Prior art: tenets, charters, ADRs, RFC 2119, agent instruction files

*Sweep key: `prior-art-governance`*

Every discipline that has studied this converges on the same architecture and, strikingly, on the same order of magnitude. The architecture: no working system uses one stopping rule - CAT, BED-LLM, and the repo's own clarify.md each OR together a quality condition, a hard budget cap, and an escape hatch. The magnitude: 5 questions (clarify.md cap), 5 users for 85% of problems (Nielsen), 3-field form sweet spot, saturation first assessable at 6 interviews, code saturation at 9, and a fatigue cliff that is steepest before question 15. For a constitution template with roughly 8 fillable slots, a budget of 5-9 recommendation-first questions is what the entire evidence base supports.\n\nThe six asks, answered concretely. (1) Elicitation stopping: laddering supplies a per-thread depth stop (probe until the terminal value / ceiling signal, then stop rather than fabricate depth) that must sit alongside the global budget; the Five Whys is documented as non-reproducible and blame-seeking, so never use a fixed-depth why-chain - use "how" probes over a flat, slot-driven breadth scan. (2) Saturation transfers as real arithmetic: base size 4, run length 2, stop when new information is <=5% (or 0%) - i.e. stop after two consecutive answers that add nothing to the draft; and note that breadth saturates at ~9 while depth needs 16-24, so a bounded pass should target breadth only. (3) Adaptive testing gives the sharpest transferable rule: PSER's two thresholds (keep going if any question would cut error by >=0.03, stop if none would cut it by >=0.01), which lets one rule both truncate and extend - and BED-LLM shows an LLM that ranks candidate questions by expected information gain beats greedy prompting 95% vs 33%, stopping when the hypothesis set collapses rather than when a counter runs out. (4) Fatigue numbers are real and unforgiving: time per question falls 75s -> 40s -> 30s -> 19s across a survey, abandonment jumps past 7-8 minutes, and drop-off rises fastest across the first 15 questions - with Krosnick's satisficing as the mechanism, meaning an over-long interview yields a constitution the user rubber-stamped rather than chose. (5) The five stopping patterns and their tradeoffs are each sourced with a stated cost - hard cap (simple, but over-asks easy cases and under-asks hard ones), coverage-complete (equal quality, variable length, needs a guard), marginal-gain (best quality-per-question, needs a predicted-change estimate), user exit (respects autonomy, but silently under-specifies unless paired with explicit Deferred reporting as clarify.md does), time-box (predictable, blunt). (6) Inference-first has excellent prior art: the NHS seven-point necessity test with its three escape valves - get it from another system, ask only to confirm, or defer it - plus GOV.UK's written question protocol, NN/g's pre-populate-with-the-common-value rule, and progressive profiling's "don't ask what you can infer".\n\nThe strongest design implication: because the constitution template has a small fixed slot count, coverage-complete is genuinely checkable here in a way it is not for an open-ended spec. That means coverage should be the primary stop condition, marginal gain the early-exit, and the numeric cap only a backstop - and the interview should read the repo first, pre-fill every slot it can, and spend its scarce questions solely where the repo is silent or contradictory.

- **No production system uses a single stopping rule. Every mature one ORs 3-4 conditions together: a precision/coverage condition, a hard budget cap, and an escape hatch. CAT stops on "SE below threshold OR max items"; BED-LLM stops on "hypothesis set collapses to one candidate OR 20 questions exhausted"; the in-house clarify.md stops on "all critical ambiguities resolved OR user says done OR 5 questions asked".**
  - *Evidence:* c:/Work/spec-kit-for-human-team-v1/templates/commands/clarify.md#L175-L178; <https://pmc.ncbi.nlm.nih.gov/articles/PMC3028267/>; <https://arxiv.org/html/2508.21184v1>
  - *Implication:* Do not pick one stopping rule for the constitution interview. Specify a disjunction and write it literally into the command file: stop when (a) every template slot has a committed answer, OR (b) the last two answers changed nothing material in the draft, OR (c) the user says stop, OR (d) the hard cap is hit. The cap is the backstop, not the primary rule - if the cap is what usually fires, the coverage rule is mis-specified.
- **The best-documented marginal-information-gain rule is PSER (Predicted Standard Error Reduction), which uses TWO thresholds, not one: keep asking if any remaining item is expected to cut the standard error by >= 0.03 (hyper), and stop early if no remaining item would cut it by >= 0.01 (hypo). It "administers fewer items when predictive gains in information are small and increases measurement precision when information is abundant."**
  - *Evidence:* <https://pmc.ncbi.nlm.nih.gov/articles/PMC3028267/>
  - *Implication:* Two thresholds beat one because they let the rule both extend and truncate. Concrete transfer: before asking question N, the agent predicts what the answer would change in the constitution draft. If no candidate question would change a principle, a constraint, or a governance rule, stop immediately even if slots remain unfilled (hypo). If a candidate question would rewrite a whole principle, ask it even if the budget is nominally spent (hyper). This is the only rule in the corpus that can justifiably exceed a cap.
- **The CAT standard-error stopping rule terminates when SE of the trait estimate falls below a fixed threshold, commonly 0.3 (corresponding to reliability 0.90). Its tradeoff is stated explicitly: it "typically yields near equivalent measurement precision across the examinee trait continuum" but "may waste items on some examinees or sacrifice precision by stopping prematurely when informative items remain."**
  - *Evidence:* <https://pmc.ncbi.nlm.nih.gov/articles/PMC3028267/>
  - *Implication:* The precision-threshold pattern gives every user an equally complete constitution but a variable-length interview. That is the right default for a document that downstream commands depend on. But it needs a max-items guard, because a vague or contradictory user can push the interview arbitrarily long - which is exactly the failure the hard cap exists to prevent.
- **The fixed-length (hard cap) rule's stated advantage is simplicity; its stated cost is that it "results in variable measurement error across trait levels and may administer unnecessary items" - it over-asks the easy cases and under-asks the hard ones.**
  - *Evidence:* <https://pmc.ncbi.nlm.nih.gov/articles/PMC3028267/>
  - *Implication:* A pure "always ask exactly 5" rule is the worst option on quality and the best on predictability. Since the constitution interview is a one-shot, high-stakes document, use the cap only as the outer bound and let coverage/marginal-gain fire earlier. clarify.md already does this correctly - the cap is the third of three OR-ed conditions, not the first.
- **The minimum-information rule stops when no remaining item can supply a preset minimum information level (threshold 0.5 in the study), and "typically delivers less accurate measurement precision than the minimum standard error stopping rule."**
  - *Evidence:* <https://pmc.ncbi.nlm.nih.gov/articles/PMC3028267/>
  - *Implication:* A pool-exhaustion rule ("stop when no remaining question is worth asking") is cheaper to implement than a precision rule but demonstrably less accurate. If the constitution interview uses only "I have no more good questions", expect systematically under-specified constitutions. Pair it with a coverage checklist over the template slots.
- **Qualitative research has a fully operational, arithmetic saturation stopping rule with three parameters: base size (default 4 interviews), run length (2 or 3), and a new-information threshold (<= 5% or 0%). Rule: count new themes in the successive run, divide by the base themes; "when this proportion <= 5% (or 0%), saturation has been reached." With base 4 and run 2, saturation is first assessable after 6 interviews; their datasets hit it at 6+2 to 9+2.**
  - *Evidence:* <https://journals.plos.org/plosone/article?id=10.1371%2Fjournal.pone.0232076>
  - *Implication:* This is the single most directly portable rule. Concrete transfer: after a base of ~4 questions, track how much each new answer adds to the draft. Stop when 2 consecutive answers add no new principle, constraint, or governance rule (0% threshold) or only a trivial refinement (<=5%). It also gives the minimum sensible interview length - you cannot even evaluate the stop condition before question 6, which argues against a cap lower than 6.
- **Guest, Bunce & Johnson (2006) found 70% of 114 themes appeared in the first 6 interviews and 92% within the first 12; a 2021 systematic review of empirical saturation tests found an average of 12-13 across all tests. Hennink, Kaiser & Marconi (2017) split this: code saturation ("heard it all") at 9 interviews, but meaning saturation ("understand it all") at 16-24.**
  - *Evidence:* <https://journals.sagepub.com/doi/10.1177/1525822x05279903>; <https://pmc.ncbi.nlm.nih.gov/articles/PMC9359070/>
  - *Implication:* Breadth saturates roughly twice as fast as depth. For a constitution interview this argues for a two-tier design: one bounded pass that enumerates the principles (breadth, ~6-9 questions, matching code saturation) and an explicitly optional, user-invoked second pass that deepens any single principle. Do not try to reach depth inside the bounded pass - the evidence says it costs 2x the questions.
- **Nielsen's diminishing-returns model, Found(n) = N * (1 - (1-L)^n) with L ~= 31% problems found per participant, yields 85% of usability problems at n=5; users 6 and 7 add roughly 4% and 2%. Nielsen's actual recommendation is not "5 is enough" but that three rounds of 5 beats one round of 15.**
  - *Evidence:* <https://www.nngroup.com/articles/why-you-only-need-to-test-with-5-users/>
  - *Implication:* Two things transfer. First, 5 is the empirically defensible knee of an exponential-saturation curve, which independently justifies clarify.md's cap of 5. Second, and more important for the constitution: iterate rather than extend. Ship a 5-9 question interview that produces a v1 constitution, then make re-running it cheap (amendment flow), instead of building one long interview. A constitution is amendable by design - lean on that.
- **SurveyMonkey's analysis of 100,000 surveys shows time-per-question decays monotonically: 75s on Q1, 40s on Q2, ~30s for Q3-10, 25s for Q11-15, 21s for Q16-25, 19s for Q26-30. For surveys over 30 questions, average time per question is "nearly half" that of surveys under 30 questions.**
  - *Evidence:* <https://www.surveymonkey.com/curiosity/survey_completion_times/>
  - *Implication:* Answer quality degrades continuously from question 2 onward - there is no safe plateau. The most valuable questions must come first, ordered by impact, not by document order. clarify.md already does this with its (Impact * Uncertainty) ranking; the constitution interview must inherit it rather than walk the template top-to-bottom.
- **Survey abandonment rises sharply past 7-8 minutes of elapsed time, with completion rates "dropping anywhere from 5% to 20%". Ten questions is roughly 5 minutes; 26-30 questions is 9-10 minutes.**
  - *Evidence:* <https://www.surveymonkey.com/curiosity/survey_completion_times/>
  - *Implication:* This is the empirical basis for a time-boxed stopping rule and it converts directly to a question budget: ~10-14 questions is the outer edge of the safe zone for a self-paced respondent. For an interview whose output is a governance document the user must actually believe in, budget well under that - 5-9 questions - and state the expected duration up front so the user can commit.
- **The drop-off/length relationship is non-linear: "the sharpest increase in drop-off rate occurs with each additional question up to 15 questions," after which marginal impact diminishes; past 35 questions respondents are relatively indifferent to further length. Study covered 100,000 surveys, 2,000 at each question count from 1 to 50.**
  - *Evidence:* <https://www.surveymonkey.com/curiosity/survey_questions_and_completion_rates/>
  - *Implication:* Every question in the 1-15 range is expensive - the exact range a constitution interview lives in. There is no "one more won't hurt" zone. Each question must clear a materiality bar before being asked, which is the qualitative version of the PSER hypo threshold and is already encoded in clarify.md lines 125-127 and 134.
- **Krosnick's satisficing theory explains the mechanism: as task difficulty rises and motivation falls, respondents shift from optimizing to weak satisficing (executing all cognitive steps less diligently, picking the first acceptable answer) and then strong satisficing (skipping steps entirely, taking cues for the easiest justifiable answer - agreeing, endorsing the status quo, saying "don't know").**
  - *Evidence:* <https://onlinelibrary.wiley.com/doi/abs/10.1002/acp.2350050305>
  - *Implication:* Strong satisficing is the specific failure mode of an over-long constitution interview: the user starts accepting every recommended default without reading. That produces a constitution that looks complete and is not owned by anyone. Design a detector - if the user accepts N consecutive recommendations verbatim with no edits, that is a satisficing signal; either stop, or switch to summarizing what has been assumed and asking for one confirmation.
- **BED-LLM terminates on hypothesis collapse, not on budget: the questioner commits when "the filtered hypothesis set collapses to a single candidate," with the 20-question limit as a fallback. Selecting each question by maximum expected information gain lifted 20-questions success from 33% (naive prompting) to 95% on Animals and from 14% to 91% on Celebrities with Mistral-Large.**
  - *Evidence:* <https://arxiv.org/html/2508.21184v1>; <https://arxiv.org/abs/2508.21184>
  - *Implication:* Direct evidence that an LLM asking questions chosen greedily is far worse than one that ranks candidates by expected information gain - roughly 3x to 6x on task success. The constitution interview should explicitly generate a candidate question pool and rank it before asking, and should stop when the remaining design space collapses (only one plausible constitution remains consistent with the answers), not when the counter hits 5.
- **BED-LLM's practical recipe: sample M=15 candidate questions per turn at high temperature (T=1.3) for diversity, optionally conditioned on a sampled hypothesis set, then pick the one maximizing EIG - explicitly designed so a question "divides the hypothesis pool into roughly balanced subsets."**
  - *Evidence:* <https://arxiv.org/html/2508.21184v1>
  - *Implication:* An implementable LLM-native heuristic that needs no probability math in the prompt: prefer the question whose plausible answers would split the space of possible constitutions most evenly. A question where you can already predict the user's answer with high confidence has near-zero information gain - skip it and record it as an assumption instead. This is the operational form of "do not ask what you can infer".
- **Information theory bounds the budget exactly: each yes/no question yields at most one bit and halves the search space, so k questions distinguish at most 2^k outcomes; any algorithm needs at least H(pi) queries on average, and Huffman-style questioning achieves under H(pi)+1.**
  - *Evidence:* <https://arxiv.org/abs/1611.01655>; <https://www.av8n.com/physics/twenty-questions.htm>
  - *Implication:* Use this to size the cap from the artifact, not from taste. Multiple-choice questions with 4-5 options carry ~2-2.3 bits each, so 5 such questions span ~1,000 distinct constitutions and 7 span ~10,000. If the space of constitutions the template can express is smaller than that, 5-7 well-chosen multiple-choice questions is provably sufficient - and any question whose answer you can predict contributes ~0 bits, so it is pure fatigue cost.
- **The NHS digital service manual gives a seven-point necessity test that must ALL pass before a question is included (you need it to deliver the service; why you need it; who uses it and how; which users must give it; how you check accuracy; what happens on a wrong/absent answer; how you keep it current and secure), plus the flat rule: "If you do not know how you'll use an answer, find out or remove the question." It also mandates inference-first: "Investigate whether you can get some of the information you need from another NHS system," use what the organisation already holds and only ask users to confirm accuracy, and "If you do not need information right now, consider collecting it afterwards."**
  - *Evidence:* <https://service-manual.nhs.uk/content/how-to-write-good-questions-for-forms/make-sure-you-need-each-question>
  - *Implication:* This is the best-specified inference-first prior art and it maps cleanly. Before asking anything, the constitution interview should read the repo (languages, test frameworks, CI config, existing AGENTS.md/CLAUDE.md, package manifests, license, branch protection) and pre-fill every slot it can. Then ask only about slots where the repo is silent or self-contradictory. The three escape valves - infer it, confirm it instead of asking it, or defer it to a later amendment - should be tried in that order for every candidate question.
- **GOV.UK mandates a "question protocol" - a written list justifying every question, which "forces you (and your organisation) to question why you're asking users for each item of information" - and structurally, "Start by splitting the form across multiple pages with each page containing just one thing" (one piece of information, one decision, or one question).**
  - *Evidence:* <https://www.gov.uk/service-manual/design/form-structure>; <https://www.gov.uk/service-manual/design/designing-good-questions>
  - *Implication:* Two design mandates. First, the command file should contain an explicit, reviewable justification for each question slot - the constitution equivalent of a question protocol - so questions cannot accumulate silently over versions. Second, one-question-at-a-time is a government-standard pattern, not a stylistic preference, which independently validates clarify.md line 141.
- **NN/g's guidance on defaults is to "pre-populate fields with the most common value if you can determine it in advance," noting the pre-filled value doubles as just-in-time instruction by showing users what a valid answer looks like - with the caveat not to exploit defaults self-servingly ("if you consistently pick the most expensive option as the default, you'll lose credibility"). Secondary sources citing Jared Spool put the share of users who change a default at under 5%.**
  - *Evidence:* <https://www.nngroup.com/articles/the-power-of-defaults/>; <https://uxplanet.org/the-power-of-defaults-992d50b73968>
  - *Implication:* Defaults are extremely sticky, which cuts both ways for a constitution. Recommendation-first questioning genuinely reduces effort and teaches the answer format - but if almost nobody edits, the recommended answer effectively IS the constitution. So the recommendations must be defensible on their own, and the interview must end with a review-and-edit pass over the assembled document rather than treating each accepted default as informed consent.
- **The in-house clarify.md already implements the recommendation-first pattern that converts questions into confirmations: for multiple choice it requires "**Recommended:** Option [X] - <reasoning>" above the options table, for short answers "**Suggested:** <your proposed answer> - <brief reasoning>", and lets the user answer with just "yes" / "recommended" / "suggested".**
  - *Evidence:* c:/Work/spec-kit-for-human-team-v1/templates/commands/clarify.md#L148-L174
  - *Implication:* This is inference-first applied to things that cannot be fully inferred: it downgrades a question (high cost) to a confirmation (low cost). Reuse it verbatim in the constitution interview. It is also what makes a 5-9 question budget feel short in wall-clock time - a confirmation costs a single word, so the per-question fatigue cost measured in surveys does not transfer at full strength.
- **clarify.md's coverage taxonomy (11 categories, each marked Clear/Partial/Missing to build an internal coverage map) plus its prioritized-queue selection - candidate questions only where a category is Partial or Missing, filtered to those that "materially impact" the outcome, and ranked by an explicit (Impact * Uncertainty) heuristic when more than 5 remain - is a complete, working implementation of the coverage-complete stopping pattern.**
  - *Evidence:* c:/Work/spec-kit-for-human-team-v1/templates/commands/clarify.md#L73-L138
  - *Implication:* Do not invent a new mechanism. Build the constitution interview's taxonomy from the constitution template's own slots (5 principle slots, 2 free-form sections, governance), score each Clear/Partial/Missing against what the repo already reveals, and ask only into Partial/Missing slots. Because the template has a fixed, small slot count, coverage-complete is actually checkable here - which it is not for an open-ended spec - so it can safely be the PRIMARY stop condition with the cap demoted to a backstop.
- **clarify.md pairs the user-controlled exit with a mitigation that removes its main downside: it honours early termination signals ("stop", "done", "proceed") but requires that "If quota reached with unresolved high-impact categories remaining, explicitly flag them under Deferred with rationale," and reports a per-category coverage table of Resolved / Deferred / Clear / Outstanding.**
  - *Evidence:* c:/Work/spec-kit-for-human-team-v1/templates/commands/clarify.md#L229-L239, #L275-L284
  - *Implication:* The tradeoff of a user-controlled exit is silent under-specification - the user bails and nobody knows what is missing. Explicit deferral converts that into a visible, actionable gap list. Copy this exactly: whenever the constitution interview ends early for any reason, it must emit the list of template slots left unfilled and what was assumed for each, so the constitution carries its own uncertainty.
- **Laddering (means-end chain) has a per-thread stopping rule distinct from any global budget: keep asking "why is that important to you" - typically five to seven times - until the respondent reaches a terminal value and can go no deeper ("it just is"), and the moderator is trained to recognise ladder-ceiling signals (repetition, vague terminal answers, performative values) and "stop the ladder at the right rung rather than fabricating depth."**
  - *Evidence:* <https://www.uxmatters.com/mt/archives/2009/07/laddering-a-research-interview-technique-for-uncovering-core-values.php>; <https://pure.au.dk/ws/files/32299631/wp34.pdf>
  - *Implication:* A bounded interview needs two independent stopping rules: a global budget and a per-thread depth stop. Detectable ceiling signals for the constitution interview: the user repeats an earlier answer, gives a non-committal answer, or restates the question back. On any of these, abandon that thread and move to the next uncovered slot instead of probing further - continued probing past the ceiling manufactures fake requirements.
- **The Five Whys is documented as unreliable for exactly the reason a fixed-depth probe is tempting: "Results are not repeatable - different people using 5 Whys come up with different causes for the same problem," it forces a linear single-cause chain onto non-linear events, and it stops at symptoms. John Allspaw's fix is to replace "why" with "how": "Asking 'why?' too easily gets you to an answer to the question 'who?' (which in almost every case is irrelevant)... Asking 'how?' gets you to describe (at least some) of the conditions that allowed an event to take place."**
  - *Evidence:* <https://www.infoq.com/news/2015/02/five-why/>; <https://blog.thinkreliability.com/top-criticisms-of-the-5-why-approach>
  - *Implication:* Do not build the constitution interview as a fixed-depth why-chain. Two concrete rules: (1) phrase probes as "how would that work" / "what would that rule out", not "why" - why-questions drift toward blame and personal preference, how-questions produce testable constraints, which is exactly what a constitution needs; (2) because a linear chain is non-reproducible, keep the branching structure flat and slot-driven (breadth over the template) rather than deep over one answer.
- **Industry aggregate data on form length shows a non-linear conversion cliff: roughly 25.5% at 1 field, ~25% at 3, ~23% at 4, ~20% at 5, ~15% at 6, ~12% at 7+, under 10% at 10+ - three fields is the commonly cited sweet spot. (Vendor/agency blog aggregation, not peer-reviewed; directionally consistent with the verified SurveyMonkey non-linearity.)**
  - *Evidence:* <https://foundrycro.com/blog/form-conversion-rate-benchmarks-2026/>; <https://neilpatel.com/marketing-stats/conversion-rate-by-form-fields/>
  - *Implication:* Treat as corroborating shape, not as a citable number. The shape matters: the first few questions are nearly free and cost accelerates after ~4-5. That supports front-loading 3-4 high-impact questions that alone produce a usable constitution, then treating everything beyond as optional depth the user can opt into.
- **Progressive profiling is the established commercial pattern for this exact problem - collect the same data in smaller, better-timed increments across interactions rather than all at once - and its standard heuristics are explicitly inference-first: "Don't ask for what you can infer. Country from IP, language from browser, role from email domain," with enrichment auto-completing fields so users "only have to enter information not available anywhere else."**
  - *Evidence:* <https://www.typeform.com/blog/progressive-profiling-collect-better-data>; <https://brixongroup.com/en/progressive-profiling-data-rich-customer-profiles-without-conversion-losses-in-b2b-marketing>
  - *Implication:* A constitution does not have to be complete on day one - it has a version field and an amendment process. Design the interview to produce a deliberately minimal v1 from 3-5 questions plus repo inference, and let subsequent commands (plan, tasks, analyze) surface the gaps that trigger a targeted amendment. This converts an unbounded interview into a bounded one plus an ongoing enrichment loop, which is exactly the pattern Nielsen's iterate-don't-extend argument recommends.

### Failure modes of standing policy documents

*Sweep key: `antipatterns`*

Spec Kit defines a constitution in spec-driven.md:276 as \"a set of immutable principles that govern how specifications become code\" acting as \"the architectural DNA of the system\", and operationally (docs/quickstart.md:52-54) as \"the ground rules... which every later step is evaluated against\". Authoring guidance is concentrated in exactly two files: templates/constitution-template.md (5 principle slots + 2 free-form sections + Governance + version footer, with inline `<!-- Example: -->` answers that read as a latent question bank) and templates/commands/constitution.md, whose steps 2-7 are effectively a scripted back end — collect/derive placeholder values, draft, produce a Sync Impact Report, validate, overwrite, summarize with a SemVer bump rationale.\n\nOn choosing principles: there is NO mandated count — the command says \"The user might require less or more principles than the ones used in the template. If a number is specified, respect that\" (line 81); the template shows 5, spec-driven.md describes 9 articles, and the repo's own constitution ratified 5. Granularity is fixed at \"succinct name line, paragraph (or bullet list) capturing non-negotiable rules, explicit rationale if not obvious\" (line 96). The quality bar is a validation pass: \"Principles are declarative, testable, and free of vague language (\\\"should\\\" → replace with MUST/SHOULD...)\" (line 110). Downstream commands enforce that bar mechanically by extracting \"principle names and MUST/SHOULD normative statements\" (analyze.md:113, converge.md:131) and treating any conflict as automatically CRITICAL (analyze.md:60).\n\nThere are three worked examples: (1) the repo's own complete, ratified constitution at .specify/memory/constitution.md — 5 principles spanning architecture/code quality, testing, CLI/UX consistency, offline performance/resources, and dependencies/file safety, plus \"Security & Cross-Platform Constraints\", \"Development Workflow & Quality Gates\", and Governance; (2) the partially-quoted \"Nine Articles\" in spec-driven.md:278-353 (Library-First, CLI Mandate, Test-First NON-NEGOTIABLE, three deliberately project-defined slots, Simplicity, Anti-Abstraction, Integration-First); (3) the template's inline comment examples. examples/ and workflows/ contain none.\n\nOn boundaries: the constitution is upstream of everything and read live, never copied — plan-template.md carries the pointer \"[Gates determined based on constitution file]\" and /plan re-derives gates each run; docs/upgrade.md:211-230 records that propagation into templates was deliberately removed because it \"duplicated the single source of truth\". Agent context files are on the far side of a hard line: \"Spec Kit itself never touches your agent context file\" (extensions/agent-context/README.md:7) — an opt-in extension writes only a marker-delimited block containing the current plan path. The template states the split directly: compliance-verified non-negotiables in the constitution, \"[GUIDANCE_FILE] for runtime development guidance\" (templates/constitution-template.md:47).\n\nOn failure modes: no doc sets any length or word budget, but the project plainly anticipates unfilled and ignored constitutions — converge.md:87-88 says \"If the constitution is an unfilled template, skip constitution checks gracefully rather than failing\", every consuming command guards with \"IF EXISTS\", and docs/upgrade.md:247 warns that frozen pre-filled gates \"can bias the first /plan pass\". The newsletters curate third-party criticism naming instruction bloat, context rot, verbosity, review overload, and a popular 4-step workflow that drops the constitution step entirely.\n\nFor interview design, the decisive fact is that the shipped command does not interview at all: it says \"If user input supplies a value, use it. Otherwise infer from existing repo context\" (lines 83-85), asking only for an unknown ratification date. The interview belongs between step 1 and step 3, replacing inference with elicitation while leaving the Sync Impact Report / validation / write / summary back end untouched. The house interview pattern already exists in clarify.md (max 5 questions, exactly one at a time, multiple-choice tables, materiality filter, explicit stop conditions), and for brownfield projects the strongest elicitation frame is the repo's own line: \"These principles are derived from the patterns the codebase already enforces.\"

- **Spec Kit's canonical definition of a constitution: "At the heart of SDD lies a constitution—a set of immutable principles that govern how specifications become code. The constitution (`memory/constitution.md`) acts as the architectural DNA of the system, ensuring that every generated implementation maintains consistency, simplicity, and quality."**
  - *Evidence:* c:/Work/spec-kit-for-human-team-v1/spec-driven.md:276
  - *Implication:* The interview must produce principles framed as *governing constraints on how specs become code*, not as a mission statement or a style guide. Every question should be answerable in a way that constrains future implementation decisions. If an answer cannot bind a future spec/plan, it does not belong in the constitution.
- **The constitution is explicitly framed as more than rules: "The constitution isn't just a rulebook—it's a philosophy that shapes how LLMs think about code generation" — with four stated value axes: "Observability Over Opacity", "Simplicity Over Cleverness", "Integration Over Isolation", "Modularity Over Monoliths".**
  - *Evidence:* c:/Work/spec-kit-for-human-team-v1/spec-driven.md:405-410
  - *Implication:* An "X over Y" trade-off framing is a natural interview question shape sanctioned by the repo's own prose. Asking "when these two conflict, which wins?" produces exactly the declarative, decidable statements the validation gate demands.
- **Immutability is a stated property, but only of the principles, not of their application: "The constitution's power lies in its immutability. While implementation details can evolve, the core principles remain constant." It claims four benefits: "Consistency Across Time", "Consistency Across LLMs", "Architectural Integrity", "Quality Guarantees".**
  - *Evidence:* c:/Work/spec-kit-for-human-team-v1/spec-driven.md:380-387, and 389-391 ("While principles are immutable, their application can evolve")
  - *Implication:* The interview should test each candidate principle for durability: "will this still be true in a year / after a framework change?". Anything version- or tool-specific is application detail and belongs in the plan or agent guidance file, not the constitution.
- **User-facing docs define it operationally as the ground rules evaluated at every later step: quickstart says "### Step 1: `/speckit.constitution` — set the ground rules" and "Establishes the project's guiding principles, which every later step is evaluated against. Run it once up front, passing your principles as arguments." README calls it "your project's governing principles and development guidelines that will guide all subsequent development".**
  - *Evidence:* c:/Work/spec-kit-for-human-team-v1/docs/quickstart.md:52-54; c:/Work/spec-kit-for-human-team-v1/README.md:95 and README.md:172; c:/Work/spec-kit-for-human-team-v1/README.zh-CN.md:95 (治理准则和开发指南)
  - *Implication:* The constitution is a once-per-project, up-front artifact — the only Spec Kit step with no feature scope. A guided interview therefore has a long budget (it runs once) but must reach closure, unlike per-feature clarify loops.
- **docs/reference/agentic-sdd.md:16 still says the command "keeps dependent templates in sync" — this text is STALE. docs/upgrade.md documents the opposite: "## Behavior change: `/constitution` no longer propagates into templates" ... it "updates `.specify/memory/constitution.md` and writes a Sync Impact Report, and **no longer edits** `plan-template.md`, `spec-template.md`, `tasks-template.md`, installed command files, or guidance docs."**
  - *Evidence:* c:/Work/spec-kit-for-human-team-v1/docs/reference/agentic-sdd.md:16 vs c:/Work/spec-kit-for-human-team-v1/docs/upgrade.md:211-217
  - *Implication:* Do not model the interview on the old propagate-everywhere behavior. The interview's only output artifact is the constitution file plus its Sync Impact Report; downstream artifacts read it live. Also a caution: repo docs contradict each other, so cite upgrade.md as current.
- **Analyze declares the constitution non-negotiable and unilaterally authoritative: "**Constitution Authority**: The project constitution (`/memory/constitution.md`) is **non-negotiable** within this analysis scope. Constitution conflicts are automatically CRITICAL and require adjustment of the spec, plan, or tasks—not dilution, reinterpretation, or silent ignoring of the principle. If a principle itself needs to change, that must occur in a separate, explicit constitution update."**
  - *Evidence:* c:/Work/spec-kit-for-human-team-v1/templates/commands/analyze.md:60, reinforced at analyze.md:157 ("CRITICAL: Violates constitution MUST") and analyze.md:249 ("Prioritize constitution violations (these are always CRITICAL)"); same authority clause in converge.md:85-88 and converge.md:170
  - *Implication:* Every principle the interview elicits becomes a merge-blocking gate. The interview must warn the user of that cost and should ask, per principle, "are you willing for this to block a PR?" A principle the user would not enforce should be captured elsewhere, not ratified.
- **There is NO fixed number of principles. The command explicitly defers to the user: "**IMPORTANT**: The user might require less or more principles than the ones used in the template. If a number is specified, respect that - follow the general template." The shipped template offers 5 numbered principle slots plus 2 free-form sections plus Governance; spec-driven.md separately describes "nine articles"; the repo's own constitution ratified 5.**
  - *Evidence:* c:/Work/spec-kit-for-human-team-v1/templates/commands/constitution.md:81; templates/constitution-template.md:6-41 (5 slots + [SECTION_2_NAME] + [SECTION_3_NAME] + Governance); spec-driven.md:280 ("nine articles"); .specify/memory/constitution.md:11-16 (five principles I-V)
  - *Implication:* The interview should treat 5 as the soft default (template shape), accept an explicit user count, and offer the overflow valve the template already provides: material that is not a principle goes into the two free-form sections (e.g. "Security & Cross-Platform Constraints", "Development Workflow & Quality Gates") rather than inflating the principle count.
- **The stated shape of a single principle: "Ensure each Principle section: succinct name line, paragraph (or bullet list) capturing non‑negotiable rules, explicit rationale if not obvious."**
  - *Evidence:* c:/Work/spec-kit-for-human-team-v1/templates/commands/constitution.md:96
  - *Implication:* Three interview sub-questions per principle, in order: (1) name it in a few words, (2) state the non-negotiable rules, (3) why. The rationale slot is the natural place to capture the user's story/incident that motivated the rule.
- **The stated quality bar, run as a validation pass before writing: "Principles are declarative, testable, and free of vague language (\"should\" → replace with MUST/SHOULD rationale where appropriate)." Other checks in the same step: "No remaining unexplained bracket tokens", "Version line matches report", "Dates ISO format YYYY-MM-DD".**
  - *Evidence:* c:/Work/spec-kit-for-human-team-v1/templates/commands/constitution.md:106-110
  - *Implication:* This is the interview's exit criterion, and it is the one part an interview must NOT replace — it must still run after elicitation. Declarative + testable + MUST/SHOULD keywords are the acceptance test for each answer; reject-and-reask any answer that fails it.
- **Downstream commands parse principles mechanically: analyze builds a "**Constitution rule set**: Extract principle names and MUST/SHOULD normative statements"; converge extracts "Principle names and MUST/SHOULD normative statements" and inventories "constitution principles that impose buildable obligations".**
  - *Evidence:* c:/Work/spec-kit-for-human-team-v1/templates/commands/analyze.md:113 and analyze.md:135-138; templates/commands/converge.md:129-131 and converge.md:138-139
  - *Implication:* Granularity bar, machine-derived: a principle is well-formed only if it yields (a) a stable name for citation (converge cites e.g. `Constitution II`) and (b) at least one MUST/SHOULD sentence that can generate a buildable task. The interview should validate each principle by asking the model to produce one concrete task from it; if it cannot, the principle is too vague.
- **Governance content is mandatory and separately specified: "Ensure Governance section lists amendment procedure, versioning policy, and compliance review expectations." Version bumps follow SemVer with stated meanings — MAJOR = "Backward incompatible governance/principle removals or redefinitions", MINOR = "New principle/section added or materially expanded guidance", PATCH = "Clarifications, wording, typo fixes, non-semantic refinements". Ratification date "is the original adoption date (if unknown ask or mark TODO)".**
  - *Evidence:* c:/Work/spec-kit-for-human-team-v1/templates/commands/constitution.md:86-91 and constitution.md:97
  - *Implication:* The interview needs a governance segment, not just a principles segment: who amends, what approval is required, how compliance is reviewed, and the ratification date. This is the one place the shipped command already says "ask" — the only explicit ask in the whole flow.
- **The command's default elicitation model is INFERENCE, not interview: "Collect/derive values for placeholders: - If user input (conversation) supplies a value, use it. - Otherwise infer from existing repo context (README, docs, prior constitution versions if embedded)." It asks the user only for an unknown ratification date (line 86) or when input is ambiguous between governance and non-governance intent (Scope Guard, line 29-30).**
  - *Evidence:* c:/Work/spec-kit-for-human-team-v1/templates/commands/constitution.md:83-86; templates/commands/constitution.md:22-30
  - *Implication:* This is the gap a guided interview fills. Insert the interview between step 1 (load template, find placeholders) and step 3 (draft), replacing "otherwise infer" with "otherwise ask, then infer only for what the user defers". Steps 4-7 (Sync Impact Report, validation, write, summary) should be preserved verbatim — they are already a complete back end.

### Bounded elicitation and stopping rules

*Sweep key: `elicitation`*

The constitution at `.specify/memory/constitution.md` is produced by one prompt (templates/commands/constitution.md) filling a placeholder template (templates/constitution-template.md), and seeded by Python only as opaque bytes — `ensure_constitution_from_template` resolves `constitution-template` through the preset priority stack, writes it if missing, and records a SHA-256 sidecar (`.constitution-template.json`) so any human edit permanently marks the file as authored and immune to preset re-seeding. It is the only template materialized to a live file rather than resolved on demand (src/specify_cli/presets/**init**.py:3605-3612).\n\nConsumption splits into two tiers. Three commands enforce: /plan reads the live constitution and fills plan-template.md's `## Constitution Check` section, which ships only the pointer `[Gates determined based on constitution file]` (plan-template.md:39-43), erroring on unjustified violations and routing justified ones to the Complexity Tracking table; /analyze extracts \"principle names and MUST/SHOULD normative statements\" (analyze.md:113) and hard-codes \"Violates constitution MUST\" as CRITICAL (analyze.md:157, :249); /converge mirrors that and cites principles as task source-refs like `Constitution II` (converge.md:213). Six commands (specify, clarify, checklist, tasks, implement, taskstoissues) only say \"IF EXISTS: load ... for project principles and governance constraints\" with no defined use.\n\nWhat makes a principle mechanically usable is therefore narrow and entirely textual: (1) a short numbered `###` name under `## Core Principles` so it can be extracted and cited; (2) literal MUST wording — MUST is the only enforcement trigger, and SHOULD is extracted but carries no severity rule anywhere; (3) a rule stated concretely enough to become a yes/no gate question about a specific plan, with the cheaper alternative it forbids named so Complexity Tracking can be filled; (4) no leftover `[ALL_CAPS]` tokens, since bracket tokens are converge's runtime signal for \"unfilled template — skip constitution checks\" (converge.md:87-88) while plan and analyze have no such carve-out.\n\nA vague, aspirational, or non-testable principle breaks nothing and errors nowhere — it fails silently. No code parses constitution content: scripts/ has zero occurrences of the word, src/ reads it only for hashing, and analyze's vague-adjective detector is scoped to spec/plan/tasks, not the constitution. Load-bearing structure is the path, the `###` heading level, the MUST/SHOULD keywords, and byte identity; the Sync Impact Report and the `**Version** | **Ratified** | **Last Amended**` line are producer-side governance bookkeeping that no enforcing consumer reads; whitespace is explicitly cosmetic (.gitattributes exempts the file from git whitespace checks).\n\nThere is no validation or linting of a user project's constitution anywhere. The three partial mechanisms are the advisory self-check in constitution.md:106-110, SHA-256 provenance (identity, not content), and markdownlint in CI covering only this repo's own dogfooded constitution. That constitution (.specify/memory/constitution.md:44-214) is the best in-repo worked example of the target shape. Finally, the whole runtime-resolution model is a deliberate documented decision (#3790, docs/upgrade.md:211-260) with an opt-in reversal via the constitution-sync wrap preset, and the contract is convention rather than guarantee — the bundled `lean` preset replaces /constitution and /plan and drops both the placeholder protocol and the Constitution Check gate entirely.
